# Factory manual

Factory is where a person's agents live and work: persistent agents, each with its own name, prompt, model and folder, all running on the person's own machine or server. This manual covers everything Factory can do and how to do it, both in the app and as an agent.

## What's in the app

<!-- admin: app-sidebar | The sidebar: agents and projects, folders, the working wave, unseen marks, dragging and nesting, the footer, provider usage circles. -->
### Sidebar
- At the top, on their own, are the agents that aren't in any project (the workspace's agents), such as Rivet.
- **Projects** lists projects (folder icon), each with its agents underneath. New agents always go in a project. A project can have **folders** (such as "App" for its code and "Research" for write-ups): its agents that work in the project's own folder come first, then a quiet heading for each folder with its agents under it. Click a heading to fold its agents away (it then shows how many it hides, and the wave while one works); drop an agent on a heading to put it in that folder.
- New projects and agents are set up by Rivet, which picks the prompt, model and extensions that suit what the person wants. The small "+" by **Projects**, and the one on a project's row while the pointer is on it (or on the focused project's name), open Rivet's conversation with the request started in its message box, "Set up a new project for " or "Add an agent to <project> that ", for the person to finish and send; anything already typed to Rivet stays, with the request on a new line after it. Hovering the "+" says "Ask Rivet to set it up". When there's no Rivet, or it has no model available, the "+" opens the New project or New agent form instead.
- Each agent shows as its character: a small, living shape in the agent's color (circle, square, triangle, diamond, pentagon or hexagon) with the same two eyes as every agent. Claktory picks the shape from the agent's id unless one is chosen in its settings, so renaming or moving it never changes it; Rivet starts as a blue hexagon. Its eyes show its mood: idle, glancing about and blinking now and then; thinking, looking up; running a tool, looking down at the work; something new to see, pleased; its last run failed, eyes down; no model, half-lidded; asleep after 15 minutes idle, eyes closed. The same character, smaller and resting, marks the agent wherever it's named: beside its messages, as an owner, in pickers. With reduced motion every face holds still in its mood. While the agent works, a soft wave of its color sweeps across its row, again and again, until the run ends (with reduced motion, the row is tinted in its color instead); a thin light runs along its header's colored line too.
- An agent's row shows its name and, when it has one, its **role** under it in smaller, fainter type ("Mike" over "Coordinator"); a row with a role is a little taller. The role shows the same way in the agent's header and in the Messaging panel, and faintly after the name over its messages and in pickers. Set it in the agent's settings, or when creating it with the New agent form.
- When an agent finishes (or fails) while you're looking elsewhere, its name turns bold and bright, with a dot in its color at the end of the row: something happened. Opening the agent clears it. Stopping an agent yourself doesn't mark it.
- Drag an agent onto a project to move it there, at the top level; drop it on the edge of a workspace agent's row (such as Rivet's) to move it beside it, out of any project. Its conversation moves with it, and so do the agents nested under it.
- Arrange agents by dragging: drop one on the upper or lower edge of another agent's row (a line shows where) to put it there, in any order; drop it on the middle of a row (the row is outlined) to nest it under that agent. Nested agents are indented under it; drag one between other rows, or onto the project itself, to take it back out. The arrow beside an agent with others under it collapses or expands them. A collapsed agent shows the wave while one of its hidden agents works, and shows the unseen marker when one has something new. The order, nesting and collapsing are kept by Claktory, the same on every device.
- Click a project to focus it (see below). Right-click a project for its settings: rename it, delete it, and keep its folders (rename one, point it at another path, remove it, or "Add a folder…", which asks Rivet to set it up, or opens a short form when Rivet can't run). Removing a folder moves its agents to the project's folder; no files are deleted.
- At the bottom, the cog opens **Settings**, the bag opens the **Marketplace** and the scroll opens **What's new**: every version of Claktory, newest first, on a timeline, each with its date and what it added, changed and fixed; the one running is marked "This version", and any not installed yet "Update to get it". Clicking any of them again goes back to the agent. The footer also shows "Connecting…" when the app can't reach Claktory, a sign-in in progress, and "Settings file has an error" when the settings file is broken. Clicking that offers "Restore last working settings", and **Tell Rivet**. Claktory's version is shown there in small type; on a Claktory on another machine it says which ("on mac-mini · Claktory …"). Clicking it lists the Claktories this device knows: **This Mac**, and each one on another machine it has connected to (hover one to Forget it); click one to show it. **Connect to another Claktory** takes the pairing code made for this device on that Claktory (see Settings → Devices) and connects. "Connecting…" names the machine it's connecting to, and when a Claktory no longer accepts this device, the footer says "This device isn't paired with <machine> any more" and stops trying; clicking either opens the same list.
- Wherever Claktory shows an error (a broken settings file, a run that failed, an update that didn't work or was undone, a request it refused, a sign-in that failed, remote access, a folder the explorer can't read, a failed monitor), **Tell Rivet** beside it opens Rivet's conversation with the error typed in its message box, ready to send, so Rivet can look into it and fix it. It shows only while Rivet can run.
- Text you read can be selected anywhere: the conversation (tool calls' input and output too), Claktory's notes, the panels, Settings, What's new, the Marketplace, dialogs and errors. Buttons, the sidebar and other things you click aren't. A right click selects the word under it (or keeps what's selected) and opens a menu with **Copy**; ⌘C copies too.
- Just above the cog and the bag, a small circle for each provider Claktory is signed in to, in that provider's color with its product's logo inside (Claude's for Anthropic, OpenAI's for OpenAI and Codex, OpenRouter's). They wrap onto more rows as there are more. For a subscription the ring around the logo fills as the weekly limit is used: empty at 0%, full at 100%. Hovering it shows the plan (such as "Claude Max 20x" or "ChatGPT Pro"; until it's known, how it's signed in), every limit's percentage used and when it resets, and when the numbers were last read; right after signing in it says the usage isn't read yet. If they couldn't be read, it says why and shows the last ones it had (the circle is faded); a dashed ring means there are no numbers yet. A provider signed in with an API key has no limits, so it shows just its logo, with no ring.

### A focused project
- Clicking a project focuses it: the sidebar shows only that project and its agents, with Rivet kept at the top so it's always a click away (it's the one who changes the project for you; it's there whenever there's an admin agent), and "‹ All projects" goes back to everything. Click (or right-click) the project's name at the top to rename or delete it. A new project opens focused.
- A file explorer on the right shows the project's folder (when the window is wide enough), the same one its agents work in, and updates as they change files. Each of the project's folders follows as a section of its own, headed by its name and path; the project's own folder steps aside when it's empty and the project has folders. No directory shows twice: a folder that is the project's own folder, or inside it, shows only as its own section. After them, each agent here with its own checkout (the Own checkout extension) has a section too, "Builder's checkout", with its branch and path, showing the files as that agent has them. Click a folder to open or close it. Files can't be opened yet.
- The explorer hides what the folder's `.factoryignore` lists (same syntax as `.gitignore`), such as `node_modules/` and build output. New projects get one with common entries; a folder without one hides those same entries. "Show everything" shows the hidden files too, dimmed.

### Updates
- Versions are numbered v0.1.0, v0.1.1, v0.1.2…, one up with every release; the middle number goes up (v0.2.0) when a new app and an older backend can't work together, so both update. Versions before v0.1.0 were named by date (2026.11.19-1958).
- When a new version of Claktory is published, a banner at the top says so, with an Update button, and "What's new" to see what the update brings. It can't be dismissed. A Claktory installed with the online installer checks for new versions shortly after it starts and every half hour, and downloads one before offering it; nothing is installed until you click Update.
- Updating restarts the app, and Claktory's backend when the release changed it. Agents that were working pick up where they left off, told that Factory restarted; messages waiting for them are kept. A release that only changed the app doesn't restart the backend at all.
- If a new backend doesn't start, Claktory goes back to the one before and the banner says what happened, with "Try again".
- On a Mac, the first update that finds Claktory's launch settings older than a new install's (`~/Library/LaunchAgents/dev.factory.factoryd.plist`; today: running as an interactive program, so macOS doesn't throttle it and what agents run) brings them up to date once, about a minute after it starts, and restarts the backend once more to apply them. If the updated settings don't load, the old ones are put back. What it did is in `{{home}}/bin/launch-agent.log`.
- On a Claktory on another machine, Update first brings that version's app over from it: the banner says how far it is ("Getting the app ready on mac-mini…", then how much has downloaded, then "Checking the new app…"). The app is replaced only once it checks out (its size and checksum, that it's Claktory, and its signature); the app then quits and opens again as the new version. If anything goes wrong, the banner says why, with "Try again", and nothing has changed.

### Agent view (click an agent)
- The header is tinted with the agent's color and shows its character, name (with its role under it), model and effort, and a meter of its context: tokens used out of the compaction threshold. Clicking the header opens the agent's settings: its character (a live preview, with each mood to try, then its shape, Automatic or one picked), name, role (optional; empty for none), color, prompt, model, effort, project, its folder (when the project has folders: the project's own folder or one of them), its message box hint (what the empty message box says; left empty, "Message <name>"; several lines, one example per line, take turns, each sliding up as the next comes in, and hold still while the pointer is over the box), its extensions, and "Delete agent…". Under **Extensions**, a switch turns each extension on or off for this agent, and while it's on, its options show underneath: more switches, or a list of agents (click it to choose agents from other projects, grouped by project; agents in its own project are already included, shown checked and greyed). Changes apply with Save.
- If the agent's model can't run because its provider isn't signed in, the header says "No model available", with a "Sign in…" button.
- The message box: Enter sends, Shift+Enter adds a line. What's typed and not sent stays as that agent's draft, through switching agents, opening Settings or the Marketplace, and restarting or updating the app, on this device; sending (or a command that runs) clears it. A message sent while the agent is working waits only until the agent's current step ends (a model reply, or a tool call such as a command finishing), then the agent reads it before going on. While it waits, it shows at the end of the conversation as its bubble, faded and labeled "Queued" (messages from other agents waiting for it show the same way, on the left); when the agent takes it, it turns into the normal bubble in place. The sidebar shows how many are waiting. Stop (or Esc) stops the run and clears the queue, and the faded bubbles fade away.
- Slash commands: typing "/" at the start of the message box lists the agent's commands, filtered as you type; arrows pick one, Enter (or a click) runs it, Tab completes its name to add arguments, Esc closes the list. **/clear** starts a new conversation (the old one is archived; its checklist and memory stay). **/compact** summarizes the conversation now and carries on from the summary; it can't run while the agent is working. If a command is refused, the reason shows above the box. Text starting with "/" that isn't a command is sent as a message.
- The person's messages are bubbles on the right in the agent's color. The conversation grows with the window, up to about twice a comfortable reading width. It also shows the agent's replies, its thinking, its tool calls (the calls one reply made share a block; each says on its row what it does, such as the command it runs with "+N lines" when there's more, the file it reads or whom it messages, and at the end how long it has run, ticking (for a command, also when it times out: "1m 23s · times out in 8m 37s", or "no limit" in the background), and once it's done, how long it took; click a call to expand its input and output), compaction dividers, and notices such as errors.
- An agent's proposal to Rivet shows in its conversation as a card in Rivet's color: the proposal, a box for a comment, and **Approve** (or Enter in the box) and **Dismiss**. Approved, Rivet gets your comment and the proposal as your message; if it can't (no Rivet, or Rivet has no model), why shows on the card and the proposal waits. Decided, the card says Approved or Dismissed, when, and your comment.
- Events, the messages that didn't come from the person, never look like theirs. A message from another agent comes in on the left in a bubble of that agent's color, under its character and name. Click its name or the bubble to open that agent's conversation (a drag or double-click in the bubble selects text instead); a sender that no longer exists isn't clickable. Queued messages from agents work the same. To go back, click the chip at the left of the header ("← Coordinator", naming the agent you came from), press ⌘[ or the mouse's back button; ⌘] or the forward button goes forward again, as in a browser. Agents deleted meanwhile are skipped. Picking an agent or project in the sidebar, Settings or the Marketplace starts over; the way back isn't kept, and each window has its own. Claktory's own notes (such as "Factory restarted") and finished background tasks are a single centered line; click it to see all of it, such as the task's output.

### Extension bar and panels
- A thin bar right of the sidebar has an icon for each extension turned on for the selected agent; hover one for its name. It changes as you click other agents.
- Clicking an icon opens that extension's panel on the right of the window; clicking it again, or the panel's ×, closes it. Each agent keeps its own panel open or closed, as you left it: switching agents shows that agent's panel. While a panel is open in a focused project it takes the explorer's place; closing it brings the explorer back.
- **Checklist** panel: the agent's checklist of everything it was asked to do, like a chat. Above is the history: done and dropped items under the day each was added, oldest at the top, every day back; each day's heading says how much of that day's is done. At the bottom, **Outstanding** holds everything still to do, in progress first, then blocked (waiting on the person or something outside, with what it's waiting on under it), then open, each oldest first, with the day it was added; when an item is done it moves up into its day. The top says how much is done overall. Each item shows its number, status (open, in progress, blocked, done, dropped) and owner; click an item to see its log of updates. It opens at the bottom and follows it as the agent changes things; scroll up and it holds still, with a round arrow button to jump back to the latest. It's read-only in the app.
- **Messaging** panel (the people icon): who the agent can message, and who can message it, each agent with its character, name, its project when it's another one ("Admin" for an admin agent such as Rivet, "Workspace" for another agent in no project), and, lined up at the right, whether it's working, idle or has no model, live. Each list says when it's empty (and, when other agents can't message it, that it's turned off in its settings). Change who can message whom in the agent's settings, under Extensions.
- **Memory** panel (the brain icon): what the agent remembers for itself. **Preferences** lists its rules by number, each with why and when it was learned (and changed); **Notes** lists its notes by name and summary, and clicking one opens the note; **Recent changes** says who changed what and when, newest first. It updates live as the agent writes it, and is read-only in the app. The **Factory manual** (the open book icon; Memory's "factory" instance, on for admin agents) opens the same way, read-only: just its notes, the parts of this manual kept there, each opening to its text.
- **Tasks** panel (the terminal icon): the agent's background tasks (every agent's, with whose each is, when it sees all of them): **Running** first, then **Finished** in the last day, newest first. Each shows its command, its id, when it started, how long it has run (ticking) or ran, and how it ended ("exit 0", "timed out", "stopped by the person"; failures in red). Click one to see the last lines of its output and where its log is. **Stop** on a running one stops it (its whole process group), and the agent gets the usual event that it finished, "stopped by the person". It updates live.
- **Monitors** panel (the alarm clock icon): what will prompt the agent later. **Active** monitors first, then **Paused** (paused, or failed: "Failed: its command kept failing", in red), then **Ended** in the last week. Each shows its name, what it waits for ("every 1h", "check `make test` every 5m, fires on failure"), its number, when it next fires (counting down), when it last fired and how many times, and its end ("until …", "2 of 5 fires") when it has one. Click one to see the prompt it sends and who set it. **Pause** or **Resume** and **Cancel** change it as you; if that isn't possible now, the reason shows under it. Under them, **Also wakes it** lists what else will wake the agent, such as a running background task. It updates live.
- **Database** panel (the database icon): the agent's database, read-only. At the top, where its file is; then its **Tables** and **Views** by name, each with how many rows it holds. Click one to see its columns and their types. It's empty until the agent makes tables. **Factory's records**, admin agents' view of Claktory's own records (`factory.db`, without agents' memory), shows the same way, under its own database icon.
- **Resources** panel (the gauge icon): how the machine and Claktory use its resources, sampled every minute. At the top, any alerts in effect (what admin agents were told, in red). **Machine**: processors (how busy, of how many cores), memory and swap used, and each volume Claktory uses with its free space and what of Claktory's is on it; a gauge past its alert's threshold (Settings → Resources) is red. **Last hour**: memory and processors as small lines, with the latest value. **Claktory**: its own processes (backend, supervisor, app) and the agents' background tasks, monitors' watches and commands running now, each with its agent, how busy it keeps the processors (100% is one core) and its memory. **Other processes**: the machine's biggest others by memory. **Disk** (measured every 20 minutes, with when): Claktory's data, its releases, each agent (click one for its conversations, logs, database and checkout) and each project's folders. Checkouts are copy-on-write: they share most of their blocks with the checkout they were made from, so they take less than they're counted as. A size Claktory couldn't finish measuring says "at least". Read-only.

### Marketplace (the bag at the bottom of the sidebar)
- Three kinds of things to add to Claktory: **Agent templates** (ready-made agents: a prompt, a model and the skills they come with), **Skills** (know-how an agent can pick up for one kind of task; templates come with theirs, and any agent can be given more) and **Extensions** (new capabilities for Claktory itself, added while it runs).

### Settings
- **Providers:** every model provider, whether Claktory is signed in to it, and buttons to sign in or out.
- **Defaults:** the model and effort new agents get, and the compaction threshold.

## Agents

- An agent is persistent: one conversation that continues across messages, days and restarts. It doesn't start fresh each time.
- Every agent is the same coding agent. What makes one different is its **name** (its identity, often a human first name such as "Mike"), its **role** (what it does, such as "Coordinator", shown with the name; optional), its **prompt** (instructions added to its system prompt), its **model**, its **effort** (how hard the model reasons), and its **project**.
- Changing an agent's model, effort, prompt, name, role, project or folder applies from its next step (its next model call), even in the middle of a task, and the agent is told in a short note from Factory ("Your model is now …", "Your instructions changed; the new ones are in your system prompt from now on.").
- An agent works in its project's folder, or in the workspace folder `{{workspace}}` when it's in no project. Its tools read, write and edit files and run shell commands.
- In a project with **folders** (see Projects), an agent works in one of them, or in the project's own folder. Its shell starts there, and write_file and edit_file change files only there; it can read the whole project, every folder of it. bash can't be held to its folder, so the agent is told to change files only in its own, with bash too. Its system prompt lists the project's folders, which one is its own, and the rest as read only.
- When an agent's context reaches the compaction threshold (400,000 tokens unless changed), Factory summarizes the conversation and the agent continues from the summary. A divider marks the spot.
- **Slash commands** are for the person, typed in an agent's message box: `/clear` stops the agent (as Stop does, dropping queued messages) and starts it on a new, empty conversation, so it works with no history (no bias from earlier, fewer tokens). The old conversation is archived in the agent's folder, not shown in the app; its checklist and memory stay. `/compact` summarizes an idle agent's conversation now, as if it had reached the threshold. Agents can't run commands, on themselves or others.
- Models suit different jobs: a strong reasoning model for building software, another for writing that should sound human. Each agent picks its own.
- Every agent has a **color**: blue, violet, green, pink, teal, amber, red or slate. Unless the person picks one, a new agent gets the color that looks least like any agent's color, so agents are as easy to tell apart as possible (after Rivet's blue: red, green, slate, pink…). Once all eight are taken, the one fewest agents have.
- **Events** prompt an agent the way a person's message does, but come from somewhere else: another agent, a background task that finished, one of its monitors, or Factory itself (after a restart, say). An event wakes an agent that's idle; a working agent gets it as soon as its current step ends (its model reply, or the tool call it's running), and reads it before going on. The model reads an event wrapped in an `<event source="…" from="…">` tag; a message from an agent is signed with its name and role (`from="Mike (Coordinator)"`), and from an agent in another project names that project too (`from="Ana (Frontend, Web Site)"`), or says it's from an admin agent (`from="Rivet (Admin)"`, or `from="Rivet (admin)"` with no role), and the tag gives the sender's `id` when its name doesn't.
- **Agents message each other** with the Messaging extension (see Extensions): `agents_send` by id or name (or role, when just one agent it can message has it), and `agents_status` to see who's idle or working. Agents see each other's roles with their names, everywhere: in `agents_status`, in the list of agents they can message (`Mike (mike, Coordinator)`) and in how messages are signed. The message reaches the other agent as an event from the sender, and replies come back the same way. This is how agents work together, such as a coordinator handing work to a frontend agent and a backend agent.
- **Who can message whom:** an agent sees and messages only the agents in its own project (agents in the workspace are a group of their own), plus any its `also` list grants. An admin agent sees and messages every agent. An agent that isn't reachable, or has the Messaging extension off, can't be messaged by anyone, and others don't see it at all. Grants go one way: for two agents in different projects to talk both ways, each needs the other in `also`. Each agent's system prompt lists the agents it can message as they were when its conversation (or its context, since the last compaction) began; when that changes, Factory tells it before its next step ("You can now message: Designer (designer)."), and the same for the models available.
- **Proposing to Rivet:** no agent can message Rivet, but one that reaches a conclusion Rivet should act on (the backend agents are saturated, so another is needed) proposes a message for it with `propose_to_rivet`, written to stand alone. The proposal shows in that agent's conversation, where the person approves it, with a comment if they like, or dismisses it. Approved, Rivet gets it as the person's own message: their comment, then "<Agent> (<role>) proposes:" and the proposal. Either way the agent is told, in an event from Factory.
- **Names can repeat** across projects. Agents tell them apart by id: a new agent whose name is another project's agent's id gets an id with its project in front (`app-frontend`). Sending by name picks the agent in the sender's own project; when that doesn't settle it, the sender is told the ids to choose from.
- **Background tasks:** bash's `run_in_background` starts a long command (a server, a long build or test run) and returns at once with a task id. Its output goes to `{{home}}/agents/<id>/tasks/<task>.log`, and when it ends, the agent gets an event with its exit status and the end of its output. Tasks run on their own: a restart of Factory's backend (an update, say) doesn't stop them, and the agent still gets the event when one ends. A command not run in the background gets 2 minutes (`timeout`, up to 10); one still running then moves to the background and runs on as a task, for up to 30 minutes more, and the agent gets its event when it ends, with a note to make it faster or start it in the background next time (a command that starts with `sleep` is stopped instead). A background task is stopped after 30 minutes unless its `timeout` asks for longer, up to 2 hours. Every result and task event says how long the command took ("[exit 0, 4.2s]"). Output up to 30,000 characters comes back whole; longer output gives its start and end and the path of its whole log. When a task has run 24 hours (`task_alert_hours`), the admin agent (Rivet) is told, once.
- **Rivet** is the agent every Factory starts with, in the workspace. Rivet helps the person achieve what they want with Factory: it sets Factory up for their goals (projects, agents, prompts, models and settings), answers questions about Factory and changes it for them. When the person clicks a "+" in the sidebar, their request reaches Rivet as their own message, starting "Set up a new project for" or "Add an agent to <project> that": Rivet sets it up as asked, with a prompt, model and extensions that fit. Rivet is the **admin agent**: it sees and messages every agent, in every project, and no agent can message it, because it hands out work rather than hearing back. Otherwise Rivet is an ordinary agent with its own prompt; it can be renamed, changed or deleted like any other. Its role is "Admin". Every agent Rivet creates gets a human first name, picked at random and different from the names of the other agents in its project, and a short role that says what it does.

## Extensions

Extensions are capabilities an agent has on top of its coding tools. Each is on or off per agent, with its own options; an agent with one on gets its tools and a short section in its system prompt saying how to use them. Turning one on or off, or changing its options, reaches the agent as a note before its next step, since its system prompt and tools stay as they are for the whole context so it stays cached. An extension turned on works from that step: the note brings its instructions and its tools, which the agent calls through its tool `extension_call` (`tool`, `args`) until its next context (after a compaction, or /clear) puts them in its tool list and system prompt. A turned-off extension's tools are refused at once. A new version of Factory that brings an extension on by default says so the same way.

Factory's extensions are Messaging, Checklist, Database, Memory, Monitors, Resources, Tasks, Highlights, Own checkout and Web. An extension can also have **instances**, named second uses of it that are on or off on their own: the Factory manual (`memory:factory`) is the Memory extension's, a read-only memory holding the rest of this manual (the app screen by screen, every extension, the settings file, signing in, where Factory keeps things). Admin agents such as Rivet have it unless it's turned off, and any agent can be given it; it opens a note with memory_read as it needs it. Factory's records (`database:factory`) is the Database extension's: factory.db to read with SQL, for admin agents the same way.

- **Messaging** (id `agents`; on unless turned off): messaging other agents and seeing their status. <!-- admin: ext-checklist | Checklist extension: items, statuses, owners, its tools and the nudge option. -->
- **Checklist** (off unless turned on): the agent keeps everything the person asks for as a checklist and works through it over days, so nothing is forgotten. Each item has a number (#1, #2…), text, a status (open, in_progress, blocked, done or dropped), an owner (an agent, or none) and a log of what happened to it. in_progress means someone is on it right now; blocked means it waits on the person or something outside, with a note saying on what. Tools: `checklist_add` (many items at once), `checklist_update` (status, owner, text and notes, for several items at once), `checklist_list` (outstanding items, open, in progress and blocked, unless asked otherwise; filters by status, day added, owner or text; `agent` reads another agent's checklist) and `checklist_item` (one item's history). Option: `nudge` (on unless turned off): when the agent has been idle a little while with open or in-progress items, and nothing will wake it (no message waiting, no background task running, no agent working that owns one of its items), Factory reminds it once, listing them; it isn't reminded again until something changes (an item, a message for it, an owner working). The person sees it in the agent's Checklist panel.

- **Database** (id `database`; off unless turned on; its instance **Factory's records**, `database:factory`, is on for admin agents unless turned off): a SQLite database of the agent's own, for structured data it collects or keeps track of over time (records, lists, results) and wants to query rather than reread. No agent has one by default: Rivet turns it on for agents that produce data, or that oversee projects producing data, to hold their metadata, so it has a good interface: SQL for the agent, and the Database panel for the person. It's `{{home}}/agents/<id>/database.sqlite`, made on the agent's first write; it lasts across compactions and /clear, and goes when the agent is deleted. Tools: `db_exec` (`sql`, `params` filling ?1, ?2…: CREATE TABLE, INSERT, UPDATE, DELETE; several statements at once without params, applied all or none), `db_query` (one SELECT; a header line and up to 200 rows, cells joined with " | ", and how many more there were) and `db_schema` (its tables and views with their columns and row counts, or with `table` one's CREATE statement and indexes). A call runs at most 10 seconds and a database holds at most 1 GB; ATTACH and loading SQLite extensions are refused. With **Factory's records** on, `db_query` and `db_schema` read Factory's own records, factory.db (with `instance: "factory"` when the agent has its own database too; see "Where Factory keeps things" for its tables): read only, and without the agents' memory (the `memory_` tables), which stays each agent's own even from admin agents. The person sees an agent's tables in its Database panel, and Factory's records in the Factory's records panel.

- **Memory** (off unless turned on; its instance **Factory manual**, `memory:factory`, is on for admin agents unless turned off): the agent's own memory, kept across compactions and never shared with other agents. Turn it on for agents that should learn the person's ways, such as a lead who keeps proposing things. **Preferences** are what the person wants and doesn't, each with why ("Don't propose paid CI. The agent's system prompt shows its preferences in full and its notes' summaries, as they were when its context began (fixed until the next compaction, so the cache holds); changes since are in its conversation. Memory is capped: preferences at 16,000 characters in all, notes at 100. Tools: `memory_update` (several changes at once, all or none: add, replace or remove preferences; write, edit or remove notes) and `memory_read` (`note` opens one, `q` searches, nothing shows preferences and notes' summaries as they are now). The person sees it in the agent's Memory panel.
<!-- admin: ext-monitors | Monitors extension: kinds of monitors, limits, repeat, what a fire says, its tools. -->
- **Monitors** (on unless turned off): prompts that wake the agent later. A monitor is a prompt the agent writes plus what it waits for: a time (`at`, or `in` "45m"), an interval since its last fire (`every`), a cron schedule in local time (`cron`), a command it runs every so often succeeding, failing, matching a regex or changing its output (`check`), files or folders changing (`files`), or a long-running command printing lines, all of them or ones matching a regex (`watch`). When it fires, the agent gets its prompt as an event from the monitor (`<event source="monitor" from="<name>" id="m3">`), with what happened (the check's output, the files that changed, the lines printed). Monitors are numbered m1, m2… per agent and last across restarts, compactions and /clear until they're done or cancelled; stopping the agent doesn't pause them. A monitor can end on its own (`until` a time, `max_fires`); a check fires once unless `repeat` is true (each time its condition becomes true again) or "always" (at every check where it holds), and its command gets `FACTORY_MONITOR_LAST_FIRED` (unix seconds of its last fire, or of when it was added). Time monitors wait until the agent is idle (`idle_only`) unless told otherwise. They can't flood an agent: a monitor never has more than one fire waiting, and what happens meanwhile comes with that one; every kind has a shortest period (a minute for times, 30 seconds for checks); an agent has at most 20 active monitors, 5 of them watches; and when an agent's monitors fire 30 times in an hour, the one going over is paused, with one notice. A check that can't run 5 times in a row, or a watch whose command keeps exiting at once or whose output passes 50 MB, stops with an error. Tools: `monitors_add` (several at once, all or none; `agent` sets one for another agent it can message), `monitors_list` (its monitors one line each, and what else will wake it: running background tasks, the checklist reminder; `all` adds those that ended in the last week) and `monitors_change` (pause, resume, cancel, or fire now to try the prompt). A watch's output goes to `{{home}}/agents/<id>/monitors/m<n>.log`. An agent a monitor will wake soon isn't reminded of its checklist.
<!-- admin: ext-resources | Resources extension: the machine's and Factory's processors, memory and disk, the resources tool, and the low-memory and low-disk alerts. -->
- **Resources** (id `resources`; on for admin agents such as Rivet unless turned off, off for others unless turned on): how this machine and Factory use its processors, memory and disk, for the agent to look into and tell the person about. Factory samples the machine every minute and keeps the last hour; what its data and projects take on disk is measured in the background every 20 minutes. Factory's own processes are told apart by process group: its backend, supervisor and app, each agent's background tasks and monitors' watches, and the commands agents are running now; everything else is grouped by app or program name. Tool: `resources` (a few lines: processors, memory, swap and each volume's free space, Factory's processes, the other programs using the most memory, alerts in effect; `detail`: `processes` for every one of Factory's process groups and the top others, `disk` for each volume and what Factory's data (releases, each agent's conversations, logs, database and checkout), and each project and folder take, or `history` for the last hour every 5 minutes). Alerts come as a Factory event to every agent with it on, once per crossing, and again only after the machine recovered: memory used above `ram_percent` for 3 samples in a row, a volume Factory uses with less free than `disk_free_gb` or `disk_free_percent` of it, whichever is smaller, and, only when `cpu_percent` is set, the processors busier than it for 5 samples. The alert tells the agent to look into it and tell the person what it finds and what they could do, and never to stop, kill or delete anything itself. Thresholds are in Settings → Resources and the settings file's `resources`. The person sees it all in the agent's Resources panel. Nothing is stored: the history starts again when Factory restarts.

Tools: `tasks_list` (one line per task, such as "task-3 builder: npm run dev — running 26h"; its own running ones, `all` adds those that ended in the last day, and `agent`, an id or "*", lists another's or everyone's) and `tasks_stop` (`task`, and `agent` for another's): it stops the task's whole process group, and the task's agent gets the usual event that it finished, "stopped by" whoever stopped it. Option: `see_all` (it can see and stop every agent's tasks; an admin agent can anyway).

Tool: `highlight` (`targets`: a list of `{kind, id}`, with kinds `agent` (an agent's id), `project`, `checklist_item` (`"<agent id>#<number>"`), `extension` (`"<agent id>/<extension id>"`, that extension's icon for the agent), and `settings` and `marketplace` (no id); `text`: an optional short caption). <!-- admin: ext-own-checkout | Own checkout extension (tree): an agent's own git checkout and branch, tree_land, when checkouts are made and removed. -->
- **Own checkout** (id `tree`; on unless turned off): the agent works in its own checkout of its project's git repository, on its own branch `factory/<agent id>` (a Factory in another home folder names its branches after it, such as `factory-dev/<agent id>`, so two Factories never share one), so agents working in parallel don't step on each other's edits and builds. An agent whose folder isn't in a git repository works there as before (its system prompt says why it has no checkout). Turn it off for an agent that should work in the main checkout itself, such as one that builds releases from it. Before the agent's first run with it, Factory makes the checkout (the agent's conversation says so, and the agent starts once it's ready) in `{{home}}/trees/<agent id>/<repository folder name>`: the files git tracks, as they are in the branch, copy-on-write where the disk allows (APFS on a Mac, btrfs or XFS on Linux), so it takes almost no space; elsewhere, or on another volume, git writes them. Nothing git ignores comes along (build output such as `target/` or `node_modules/`, local settings), so making one takes moments however big the build output is, and the first build in it is a full one. The agent works in the same place in it as in the project, may read the main checkout but not change it with its file tools, and keeps the checkout across days. It commits there, rebases onto the main branch, and lands its work with the tool `tree_land`, which fast-forwards the main checkout's branch to its branch (refused, saying why, if the main branch moved on or changes there would be overwritten). When the agent is deleted or the extension turned off, its checkout and branch are removed, unless it has uncommitted changes or commits not landed: then they're kept. Agents never make git worktrees or copies of a repository themselves; this is how an agent gets a checkout of its own.
<!-- admin: ext-web | Web extension: web_search and web_fetch, how searches are paced and blocks waited out, what fetch refuses. -->
- **Web** (id `web`; on unless turned off): the agent searches the web and reads pages, as a browser on this computer would, with no account or key. Tools: `web_search` (`queries`: 1 to 4; `domains`: `example.com` keeps only that site, `-example.com` leaves it out; `recency`: day, week, month or year; `limit`: results per query, 8 unless asked, at most 10) gives each result's title, URL and snippet. `web_fetch` (`url`, and `offset` or `find`) reads a page (HTML, Markdown, text, JSON or PDF) as numbered Markdown lines, about 20,000 characters at a time; with `find` (several separated by `|`) only the matching lines, with the lines around them. Searches go to DuckDuckGo, and to Brave when DuckDuckGo can't answer. Every agent searches from the same computer, so searches are paced for the whole Factory (a few seconds apart on DuckDuckGo, about 20 on Brave, each with an hourly budget). An engine that blocks (a CAPTCHA, a rate limit) isn't asked again for an hour or more; while none can answer, web_search says which and until when. Searches are kept for an hour and pages for 15 minutes, so asking again costs nothing. web_fetch reads only public pages, never this computer, its network or a bare host name; it follows redirects within a site and reports one to another site, for the agent to fetch if it wants.

## Projects

- A project is a folder in the workspace, named after the project: "Web Site" lives in `{{workspace}}/web-site`. Creating a project only asks for its name.
- Renaming a project keeps its folder. Deleting a project deletes its agents and their conversations, but never the files in its folder.
- A project can have **folders**: places inside it where some of its agents work, each with a name and a path anywhere on the machine. The Factory project, say, could have "App" (a code repository elsewhere) for its coordinator and developers, and "Research" for its researcher's write-ups. Folders only scope where agents work: messaging, extensions and everything else stay project-wide. A folder added without a path goes inside the project's folder, named after it; it's created if missing. Removing a folder moves its agents to the project's own folder and never deletes files.

## Factory on another machine

Factory's backend can run on an always-on machine (a Mac mini, a Linux server) and serve the app on other devices, so agents keep working while the laptop sleeps or travels. Every device shows the same Factory.
- Turn on the remote listener on the machine running Factory: in its app, Settings → Devices → **Remote access** (the port and the address to listen on are there too). Or add `"remote": {"port": 7443}` to the settings file, and `"listen": "<address>"` to listen on one address only, such as the machine's Tailscale address (100.x.y.z), which keeps it off the local network. Or run `{{home}}/bin/factoryd remote on` there (port 7443, or `remote on <port>`; `remote off` turns it off again). It starts within a second, and stops when it's taken out. Without `remote`, only that machine's own app can connect.
- Pair each device: in the app showing that Factory, Settings → Devices → **Pair a device…** makes its pairing code, shown once as a QR code and a link to copy; the list there shows when each device last connected, and Unpair takes one's access away at once. Or on that machine: `{{home}}/bin/factoryd pair <device name>` prints a pairing code, `factory://<address>:<port>?t=…&fp=…&name=…`, once (`--host <address>` names the address the device reaches the machine by, when Factory's guess won't do). It holds the device's key, so treat it like a password. `factoryd devices` lists paired devices and when each last connected; `factoryd unpair <device>` takes one's access away at once. Only the person, or an agent on that machine, can run these.
- On the device: click the Factory name at the bottom of the sidebar, paste the code under **Connect to another Factory** and click Connect. The device remembers it, and the same list switches back to **This Mac**, or to another Factory.
- Connections are encrypted with Factory's own certificate, which devices pin, and every device needs its key, so it's safe on any network. To reach the machine from anywhere, put both on a Tailscale network (or Headscale, or any VPN).
- The agents run on that machine: projects, git credentials, tools and sign-ins live there, and a project folder's path is one of its paths: in project settings, type it, or click Choose… to browse that machine's folders (click a folder to open it; Up, Home and the path at the top move around; Show hidden shows folders starting with "."; Choose takes the folder you're in). Keep it awake. Sign in to providers there from the app by pasting the address or code the browser ends on. Web searches come from its address.
- A device elsewhere updates with the same Update banner: its app fetches the new app from that Factory over the same encrypted connection (on a Linux machine, Factory downloads the Mac release for it first), checks it, replaces itself and reopens, and Factory's backend updates as usual. A release made before this, or one with no app, says why it can't update the app; the backend can still be updated.
- On Linux (x86_64 or aarch64, any distribution with systemd), Factory runs as its backend alone, with the app on a Mac. The same online installer as a Mac's, `curl -fsSL <channel>/install.sh | bash`, run as the person (not root), installs it as a systemd user service that starts at boot, turns the remote listener on and prints a pairing code for the first device. Open port 7443 in the machine's firewall if it has one, or use Tailscale. Updates come as on a Mac: the backend downloads them and the connected app offers them. Its log is `{{home}}/factoryd.log`.

## Changing Factory as an agent

Everything in the sidebar and Settings, except signing in, lives in the settings file `{{config}}`, and Factory applies a change to it within a second. Changing it is the admin agent's job (Rivet's), and that of agents given the full Factory manual (the Memory extension's Factory manual), whose notes say how. Other agents leave it alone, and send the person to Rivet.

<!-- admin: settings-file | The settings file: every key, the agents and projects lists, and how to add, move, change, nest or delete agents, projects, folders and extensions. -->
### The settings file

Everything in the sidebar and Settings, except signing in, lives in the settings file `{{config}}`. Edit it with your file tools and Factory applies the change within a second, in every open window. So an agent can do for the person nearly anything they could do by clicking.

```json
{
  "compact_at_tokens": 400000,
  "default_model": "anthropic/claude-opus-5-5",
  "default_effort": "high",
  "projects": [
    { "id": "web-site", "name": "Web Site", "path": "{{workspace}}/web-site",
      "folders": [ { "id": "research", "name": "Research", "path": "{{workspace}}/web-site/research" } ] }
  ],
  "agents": [
    { "id": "rivet", "color": "blue", "name": "Rivet", "role": "Admin", "prompt": "…", "model": "anthropic/claude-opus-5-5", "effort": "medium",
      "placeholder": "Set up a team that works on my codebase while I sleep\nSet up agents that build and run the website for my bakery",
      "avatar": { "shape": "hexagon" }, "extensions": { "agents": { "reachable": false, "admin": true } } },
    { "id": "nina", "color": "violet", "project": "web-site", "name": "Nina", "role": "Writer", "prompt": "Write the site's copy.", "model": "anthropic/claude-opus-5-5", "effort": "medium",
      "extensions": { "agents": { "also": ["designer"] }, "checklist": { "enabled": true } } }
  ]
}
```

- `compact_at_tokens`: the compaction threshold, above 0.
- `highlights`: `false` when the person has turned highlights off (Settings → Display); left out, they're on.
- `task_alert_hours`: how long a background task runs before admin agents are told of it, once (24 unless changed).
- `resources`: when agents with the Resources extension are told the machine runs low (Settings → Resources): `ram_percent` (memory used, 1 to 100; 90 unless changed), `disk_free_gb` and `disk_free_percent` (a volume Factory uses has less free than either, whichever is smaller; 10 and 10; `disk_free_gb` 0 turns it off) and `cpu_percent` (processors busier than it, 0 to 100; 0, off, unless changed). Every key is optional.
- `display`: how wide the person dragged the app's sidebar (`sidebar_width`) and the panel on the right (`panel_width`), in logical pixels, the same on every device; 0 or left out is the app's default, and the app keeps them within its range. Both are optional; a negative width makes the file invalid.
- `remote`: Factory's listener for devices on other machines (see "Factory on another machine"): `port`, and `listen`, an IP address to listen on only; left out, there's none.
- `default_model`, `default_effort`: what new agents get when none is chosen.
- `projects[]`: `id`, `name`, `path`, the absolute path of its folder, and `folders` (optional): each with an `id` (unique within the project), a `name` and a `path`, absolute and anywhere.
- `agents[]`: `id`, `name`, `role` (what it does, shown with its name to the person and to other agents, such as "Coordinator"; left out, it has none), `prompt`, `model` (`"<provider>/<model id>"`), `effort`, `color` (one of the eight; it belongs to the agent, so moving the agent in the list never changes it; left out, Factory picks one, as for a new agent, or keeps the one the agent had, and writes it into the file), `project` (a project's id; leave it out for the workspace), `parent` (the id of the agent it sits under in the sidebar, in the same project; leave it out for the top level), `folder` (the id of one of its project's `folders` to work in; left out, or one the project doesn't have, it works in the project's own folder), `placeholder` (what its message box says when empty, such as what the agent is for; left out, it says "Message <name>"; several lines separated by `\n` are examples that take turns, such as Rivet's), `avatar` (its character's shape, drawn in its color: `{"shape": "hexagon"}`, with shapes circle, square, triangle, diamond, pentagon and hexagon; left out, or a shape Factory doesn't know, it's automatic, picked from the agent's id so it never changes when the agent is renamed or moved; display only), and `extensions`.
- The order of `agents` is the order of the sidebar: within each project (and the workspace), and among each parent's agents, agents show in the order they come in the list. A `parent` that doesn't exist, is in another project or would make a loop is ignored (the agent shows at the top level) without making the file invalid.
- `extensions`: the agent's extension settings by extension id. Every key is optional; anything left out takes the extension's default. `enabled` turns an extension on or off for the agent. Messaging's options (under `agents`): `reachable`, `admin` and `see_map` (true or false) and `also` (a list of agent ids). Checklist's option: `nudge` (true or false). Tasks' option: `see_all` (true or false). Memory, Monitors, Resources, Highlights, Own checkout (`tree`) and Web have only `enabled`, and so do instances, by their key: `"memory:factory": {"enabled": true}` gives an agent the Factory manual, `{"enabled": false}` takes it from an admin agent. Settings for an extension Factory doesn't have are kept and ignored; a value of the wrong kind (`"admin": "yes"`) makes the file invalid.
- Ids use only a-z, 0-9 and -, and are unique among projects and among agents. Names can't be empty. Efforts are off, minimal, low, medium, high, xhigh or max; use one the model lists. Use models from the list of available ones below; others won't run.
- If an edit leaves the file invalid, Factory keeps the last good settings and the sidebar shows the error until the file is fixed. Check your edit and fix it right away.

How to:
- **Add a project:** add it to `projects` with `path` set to `{{workspace}}/<id>`, and create that folder (`mkdir -p`).
- **Add an agent:** add it to `agents`. A new agent starts with an empty conversation.
- **Move an agent:** set its `project`, or remove `project` to move it to the workspace. It works in the new folder from its next step. Its `folder` belongs to the old project, so remove it or set one of the new project's. Move the agents under it too (set their `project` as well), or they're shown at the top level of the old project.
- **Set up folders in a project:** add them to the project's `folders`, e.g. `{ "id": "app", "name": "App", "path": "/Users/me/code/app" }`, create any folder that doesn't exist yet (`mkdir -p`), and set `folder` on each agent that works there. It works there from its next step. To remove a folder, take it out of `folders` and take `folder` off its agents; its files stay.
- **Reorder or nest agents in the sidebar:** move entries within `agents` to change their order, and set `parent` to put an agent under another one in its project (remove `parent` to bring it back to the top level). Nesting only changes how the sidebar shows them; it doesn't change who can message whom.
- **Change an agent:** edit its `name`, `color`, `prompt`, `model`, `effort`, `placeholder` or `avatar`. This includes you: your own entry is how you change yourself. The change applies from the agent's next step, even mid-task, and it's told in a short note what changed. `color`, `placeholder` and `avatar` apply at once: they only change what the app shows.
- **Delete an agent or project:** remove its entry. Deleting in the app also erases the conversation; removing the entry leaves the conversation's files in `{{home}}/agents/<id>`, and an agent added later with the same id picks it back up.
- **Change defaults:** edit `default_model`, `default_effort` or `compact_at_tokens`.
- **Turn an extension on or off for an agent:** set `extensions.<id>.enabled`, e.g. `"extensions": {"checklist": {"enabled": true}}`. The agent is told before its next step; an extension turned on can be used from then on (through `extension_call` until the agent's next context), and one turned off has its tools refused at once.
- **Let an agent message agents in other projects:** add their ids to its `extensions.agents.also`; for a conversation both ways, add each to the other's. `admin: true` lets it see and message everyone; `reachable: false` stops all agents from messaging it.

Agents can't yet sign in to providers or stop other agents; those need the app. When something can only be done in the app, tell the person exactly where to click.

## Where Factory keeps things

- `{{config}}`: the settings.
- `{{workspace}}`: the workspace folder, with one folder per project.
- `<project folder>/.factoryignore`: what the explorer hides in that project.
- `{{home}}/releases/`: published versions of Factory, which the app offers as updates (built here, or downloaded by a Factory installed online). Once a device on another machine has updated from one, it also holds that version's app packed for devices (`app.tar.gz`).
- `{{home}}/factory.db`: Factory's records, in SQLite. `messages` holds every message an agent was sent, the person's and events (`source` is person, factory, agent, task or monitor; `sender`, `summary`, `text`), with when it was `created`, `delivered` and in which `run`, or `dropped` (the agent was stopped or deleted, or its model couldn't run). `runs` holds each stretch of work (`agent`, `version`, `started`, `ended`, `outcome`: finished, stopped, failed, deleted or interrupted). `tasks` holds background tasks (`agent`, `task`, `command`, `pid`, `log`, `started`, `ended`, `status`). `checklist_items` holds each agent's checklist as it is now (`agent`, `id`, `text`, `status`, `owner`, `created`, `updated`), and `checklist_events` everything that happened to the items, never changed afterwards (`agent`, `item`, `time`, `actor`: an agent id or '' for the person, `kind`: created, status, owner, edited or note, and the new `value`). `memory_preferences` (`agent`, `id`, `rule`, `why`, `learned`, `updated`) and `memory_notes` (`agent`, `slug`, `summary`, `body`, `created`, `updated`) hold each agent's memory as it is now, and `memory_events` every change to it, never changed afterwards (`agent`, `time`, `actor`, `kind`: pref_added, pref_replaced, pref_removed, note_written, note_edited or note_removed, `subject`: the preference's id or the note's slug, and the whole entry `before` and `after`, as JSON). `monitors` holds each agent's monitors as they are now (`agent`, `id`, `name`, `prompt`, `kind`, `spec`, `until`, `max_fires`, `idle_only`, `created_by`, `created`, `state`: active, paused, done, cancelled or error, `reason`, `next_due`, `last_fired`, `fires`), and `monitor_events` what happened to them, never changed afterwards (`agent`, `monitor`, `time`, `actor`, `kind`: created, fired, paused, resumed, cancelled, done or error, and `value`). `proposals` holds what agents proposed to Rivet (`agent`, `text`, `created`, `state`: pending, approved or dismissed, the person's `comment`, and when it was `decided`). `state`, `open_panels` (the panel open beside each agent), `expanded`, `show_all`, `collapsed` (agents whose agents underneath are folded away in the sidebar), `collapsed_folders` (project folders whose agents are folded away) and `unseen` (agents whose work finished since the person last opened them) hold what the app shows. `agent_presence` holds what each agent's character shows between runs: when it last became idle (`idle_since`: a run ended, /clear, or it was first seen) and whether its last run `failed`; idle 15 minutes, it shows asleep. Times are milliseconds since 1970. Read it with `sqlite3` to see what happened, such as what an agent was sent and when; Factory writes it, so don't change it. Agents that were working when Factory stopped carry on from it when Factory starts.
- `{{home}}/remote/`: what devices on other machines need: Factory's certificate (`cert.pem`, `key.pem`) and the paired devices (`devices.json`: each one's `id`, `name`, the SHA-256 of its key, when it was paired and last connected). Use `factoryd pair`, `unpair` and `devices` rather than editing it.
- `{{home}}/trees/<agent id>/`: the agent's own checkouts (Own checkout extension), one per repository, each with a `.json` beside it saying which repository it's of. Factory makes and removes them.
- `{{home}}/agents/<id>/`: each agent's conversation, its database (`database.sqlite`, Database extension), in `tasks/` its background tasks' logs, in `monitors/` its monitors' watch logs and file baselines, and in `archive/<time>/` conversations cleared with /clear (time in milliseconds since 1970). Factory writes these; don't edit them.
- The app keeps only its window's size and position, unsent drafts in the message boxes, and which Factory it shows (with the pairing codes of the others it has connected to), on each device. Everything else is in the backend, so every device shows the same Factory.
