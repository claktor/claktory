# Claktory manual

Claktory is where a person's agents live and work: persistent agents, each with its own name, prompt, model and folder, all running on the person's own machine or server. This manual covers everything Claktory can do and how to do it, both in the app and as an agent.

## What's in the app

<!-- admin: app-claktories | The rail of Claktories at the window's left: several Claktories connected at once, switching, adding, renaming and removing one; the phone's list. -->
### Claktories
- The app can be connected to several Claktories at once: this Mac's, and others on other machines (a Linux server, another Mac), each paired with this device. All of them stay connected and live; nothing is shared or merged between them, and the window shows one at a time.
- A thin rail at the window's far left has a tile for each: this Mac's (a laptop glyph) first, then the others in the order they were added, each with its name's initials ("mac-mini" is "MM"). The one showing is tinted, with an orange mark at the window's edge. Click another to switch the whole window to it at once, as it was left. Hovering one shows its name and whether it's connected.
- At a glance: a tile waves softly while one of its agents works, has a dot at its corner while one has something new, and a red dot when it can't connect or no longer accepts this device. A Claktory that isn't connected yet is faint.
- **+** at the bottom of the rail adds one: paste the pairing code made for this device on that Claktory (Settings → Devices → Add a device…), and it connects and shows.
- Right-click a tile to rename it (the name is kept on this device only; empty goes back to the machine's name: a Mac's Computer Name, from System Settings → General → Sharing, or the host name elsewhere) or, for one on another machine, **Remove…** it: this device disconnects, forgets its code and leaves that Claktory's devices. Its agents and work stay there.
- On iPhone, the Claktories are a list at the top: the one chosen opens straight away, "‹ Claktories" above its sidebar goes back to the list, with a dot when another has something new. Each row shows the name, whether it's connected or working, and news; a long press renames or removes one, and **Add a Claktory** pairs another by scanning or pasting its code.

### Sidebar
- Drag the sidebar's right edge to make it narrower or a little wider (200 to 300 points; 248 by default); double-click the edge to go back to the default. The width is kept in Claktory, so it's the same on every device.
- At the top, on their own, are the agents that aren't in any project (the workspace's agents), such as Rivet.
- **Projects** lists projects (folder icon), each with its agents underneath. New agents always go in a project. A project can have **folders** (such as "App" for its code and "Research" for write-ups): its agents that work in the project's own folder come first, then a quiet heading for each folder with its agents under it. Click a heading to fold its agents away (it then shows how many it hides, and the wave while one works); drop an agent on a heading to put it in that folder.
- New projects and agents are set up by Rivet, which picks the prompt, model and extensions that suit what {{user}} wants. The small "+" by **Projects**, and the one on a project's row while the pointer is on it (or on the focused project's name), open Rivet's conversation with the request started in its message box, "Set up a new project for " or "Add an agent to <project> that ", for {{user}} to finish and send; anything already typed to Rivet stays, with the request on a new line after it. Hovering the "+" says "Ask Rivet to set it up". When there's no Rivet, or it has no model available, the "+" opens the New project or New agent form instead.
- Each agent shows as its character: a small, living shape in the agent's color (circle, square, triangle, diamond, pentagon or hexagon) with the same two eyes as every agent. Claktory picks the shape from the agent's id unless one is chosen in its settings, so renaming or moving it never changes it; Rivet starts as a blue hexagon. Its eyes show its mood: idle, glancing about and blinking now and then; thinking, looking up; running a tool, looking down at the work; something new to see, pleased; its last run failed, eyes down; no model, half-lidded; asleep after 15 minutes idle, eyes closed. The same character, smaller and resting, marks the agent wherever it's named: beside its messages, as an owner, in pickers. With reduced motion every face holds still in its mood. While the agent works, a soft wave of its color sweeps across its row, again and again, until the run ends (with reduced motion, the row is tinted in its color instead); a thin light runs along its header's colored line too.
- An agent's row shows its name and, when it has one, its **role** under it in smaller, fainter type ("Mike" over "Coordinator"); a row with a role is a little taller. The role shows the same way in the agent's header and in the Messaging panel, and faintly after the name over its messages and in pickers. Set it in the agent's settings, or when creating it with the New agent form.
- When an agent finishes (or fails) while you're looking elsewhere, its name turns bold and bright, with a dot in its color at the end of the row: something happened. Opening the agent clears it. Stopping an agent yourself doesn't mark it.
- Drag an agent onto a project to move it there, at the top level; drop it on the edge of a workspace agent's row (such as Rivet's) to move it beside it, out of any project. Its conversation moves with it, and so do the agents nested under it.
- Arrange agents by dragging: drop one on the upper or lower edge of another agent's row (a line shows where) to put it there, in any order; drop it on the middle of a row (the row is outlined) to nest it under that agent. Nested agents are indented under it; drag one between other rows, or onto the project itself, to take it back out. The arrow beside an agent with others under it collapses or expands them. A collapsed agent shows the wave while one of its hidden agents works, and shows the unseen marker when one has something new. The order, nesting and collapsing are kept by Claktory, the same on every device.
- Click a project to focus it (see below). Right-click a project for its settings: rename it, delete it, and keep its folders (rename one, point it at another path, remove it, or "Add a folder…", which asks Rivet to set it up, or opens a short form when Rivet can't run). Removing a folder moves its agents to the project's folder; no files are deleted.
- At the bottom, the cog opens **Settings**, the bag opens the **Marketplace** and the scroll opens **What's new**: every version of Claktory, newest first, on a timeline, each with its date and what it added, changed and fixed; the one running is marked "This version", and any not installed yet "Update to get it". On a Mac each opens as a pane right of the selected agent's conversation (see Panes), so the conversation stays readable beside it; its button shows it's open, and clicking it again closes the pane. One already open glows instead of opening twice. With no agent selected, or on an iPhone, it takes the whole view, with Done (or Esc) to go back. The footer also shows "Connecting…" when the app can't reach Claktory, a sign-in in progress, and "Settings file has an error" when the settings file is broken. Clicking that offers "Restore last working settings", and **Tell Rivet**. Claktory's version is shown there in small type; on a Claktory on another machine it says which ("on mac-mini · Claktory …"). It's only text: the rail at the window's left (on an iPhone, the list of Claktories) switches and adds them. "Connecting…" names the machine it's connecting to, and when a Claktory no longer accepts this device, the footer says "<machine> no longer allows this device" and stops trying; clicking either lists the Claktories this device knows: **This Mac**, and each one on another machine it has connected to (hover one to Forget it); click one to show it. **Connect to another Claktory** there takes the pairing code made for this device on that Claktory (see Settings → Devices) and connects.
- Wherever Claktory shows an error (a broken settings file, a run that failed, an update that didn't work or was undone, a request it refused, a sign-in that failed, remote access, a folder the explorer can't read, a failed monitor), **Tell Rivet** beside it opens Rivet's conversation with the error typed in its message box, ready to send, so Rivet can look into it and fix it. It shows only while Rivet can run.
- Text you read can be selected anywhere: the conversation (tool calls' input and output too), Claktory's notes, the panels, Settings, What's new, the Marketplace, dialogs and errors. Buttons, the sidebar and other things you click aren't. A right click selects the word under it (or keeps what's selected) and opens a menu with **Copy**; ⌘C copies too.
- Just above the cog and the bag, a small circle for each provider Claktory is signed in to (for a provider with several subscription accounts, one per account), in that provider's color with its product's logo inside (Claude's for Anthropic, OpenAI's for OpenAI and Codex, OpenRouter's). They wrap onto more rows as there are more. For a subscription the ring around the logo fills as the weekly limit is used: empty at 0%, full at 100%. Hovering it shows the plan (such as "Claude Max 20x" or "ChatGPT Pro"; until it's known, how it's signed in), every limit's percentage used and when it resets, and when the numbers were last read; right after signing in it says the usage isn't read yet. If they couldn't be read, it says why and shows the last ones it had (the circle is faded); a dashed ring means there are no numbers yet. A provider signed in with an API key has no limits, so it shows just its logo, with no ring.

<!-- admin: app-focused-project | Focusing a project, and its file explorer: folders, checkouts, .factoryignore and Show everything. -->
### A focused project
- Clicking a project focuses it: the sidebar shows only that project and its agents, with Rivet kept at the top so it's always a click away (it's the one who changes the project for you; it's there whenever there's an admin agent), and "‹ All projects" goes back to everything. Click (or right-click) the project's name at the top to rename or delete it. A new project opens focused.
- A file explorer on the right shows the project's folder (when the window is wide enough), the same one its agents work in, and updates as they change files. Each of the project's folders follows as a section of its own, headed by its name and path; the project's own folder steps aside when it's empty and the project has folders. No directory shows twice: a folder that is the project's own folder, or inside it, shows only as its own section. After them, each agent here with its own checkout (the Own checkout extension) has a section too, "Builder's checkout", with its branch and path, showing the files as that agent has them. Click a folder to open or close it. Files can't be opened yet.
- The explorer hides what the folder's `.factoryignore` lists (same syntax as `.gitignore`), such as `node_modules/` and build output. New projects get one with common entries; a folder without one hides those same entries. "Show everything" shows the hidden files too, dimmed.

### Updates
- Versions are numbered v0.1.0, v0.1.1, v0.1.2…, one up with every release; the middle number goes up (v0.2.0) when a new app and an older backend can't work together, so both update. Versions before v0.1.0 were named by date (2026.11.19-1958).
- When a new version of Claktory is published, a banner at the top says so, with an Update button, and "What's new" to see what the update brings. It can't be dismissed. A Claktory installed with the online installer checks for new versions shortly after it starts and every half hour, and downloads one before offering it; nothing is installed until you click Update.
- Updating restarts the app, and Claktory's backend when the release changed it. Agents that were working pick up where they left off, told that Claktory restarted; messages waiting for them are kept. A release that only changed the app doesn't restart the backend at all.
- If a new backend doesn't start, Claktory goes back to the one before and the banner says what happened, with "Try again".
- On a Mac, the first update that finds Claktory's launch settings older than a new install's (`~/Library/LaunchAgents/dev.factory.factoryd.plist`; today: running as an interactive program, so macOS doesn't throttle it and what agents run) brings them up to date once, about a minute after it starts, and restarts the backend once more to apply them. If the updated settings don't load, the old ones are put back. What it did is in `{{home}}/bin/launch-agent.log`.
- On a Claktory on another machine, Update first brings that version's app over from it: the banner says how far it is ("Getting the app ready on mac-mini…", then how much has downloaded, then "Checking the new app…"). The app is replaced only once it checks out (its size and checksum, that it's Claktory, and its signature); the app then quits and opens again as the new version. If anything goes wrong, the banner says why, with "Try again", and nothing has changed.

### Developer Tools (faster builds on a Mac)
- macOS checks every new program the first time it runs, and agents build and run many (each test binary a build makes): a fraction of a second each, which adds up to most of a minute on a large test run. A program macOS counts as a developer tool spares everything it starts these checks.
- What agents run is started by Claktory's supervisor, which on a Mac installed (or reinstalled) with this version's installer is an app of its own, **Claktory Agents**, in `{{home}}/bin/Claktory Agents.app`. Installs from before run a bare program there instead, which macOS can't list; reinstalling Claktory (its installer again, over the installed Claktory) brings the app. Updates never change the supervisor.
- To add it: in Terminal, `spctl developer-mode enable-terminal` (once, so System Settings shows the Developer Tools list); then System Settings → Privacy & Security → Developer Tools → **+**, press ⇧⌘G, enter `{{home}}/bin/Claktory Agents.app`, click Open, and make sure it's switched on.
- To check it: have an agent run `cd "$(mktemp -d)" && printf 'int main(void){return 0;}' > t.c && cc -o t t.c && time ./t`. Without the grant the first run of a new program takes about 0.1–0.2 s; with it, a few milliseconds.
- Until Claktory's releases are signed with its Developer ID, macOS knows Claktory Agents by its exact build, so after a reinstall it needs adding again (remove the old entry with **−** first).

### Agent view (click an agent)
- The header is tinted with the agent's color and shows its character, name (with its role under it), model and effort, and a meter of its context: tokens used out of the compaction threshold. Clicking the header opens the agent's settings: its character (a live preview, with each mood to try, then its shape, Automatic or one picked), name, role (optional; empty for none), color, prompt (Rivet's says whether it's Claktory's default, and once changed, **Reset to default** puts the default back), model, effort, project, its folder (when the project has folders: the project's own folder or one of them), its message box hint (what the empty message box says; left empty, "Message <name>"; several lines, one example per line, take turns, each sliding up as the next comes in, and hold still while the pointer is over the box), its **Secrets** (a switch for each of the vault's secrets, on for those it has; the Secrets extension's box names them too), its extensions, and "Delete agent…". Under **Extensions**, a switch turns each extension on or off for this agent, and while it's on, its options show underneath: more switches, or a list of agents (click it to choose agents from other projects, grouped by project; agents in its own project are already included, shown checked and greyed). Changes apply with Save.
- If the agent's model can't run because its provider isn't signed in, the header says "No model available", with a "Sign in…" button.
- The message box: Enter sends, Shift+Enter adds a line. What's typed and not sent stays as that agent's draft, through switching agents, opening Settings or the Marketplace, and restarting or updating the app, on this device; sending (or a command that runs) clears it. A message sent while the agent is working waits only until the agent's current step ends (a model reply, or a tool call such as a command finishing), then the agent reads it before going on. While it waits, it shows at the end of the conversation as its bubble, faded and labeled "Queued" (messages from other agents waiting for it show the same way, on the left); when the agent takes it, it turns into the normal bubble in place. The sidebar shows how many are waiting. Stop (or Esc) stops the run; what's queued stays, and the agent gets it right after, as a new run. A message from you also moves a long command the agent is running to the background (another agent's, once the command has run a minute), so it's read sooner.
- Slash commands: typing "/" at the start of the message box lists the agent's commands, filtered as you type; arrows pick one, Enter (or a click) runs it, Tab completes its name to add arguments, Esc closes the list. **/clear** starts a new conversation (the old one is archived; its checklist and memory stay). **/compact** summarizes the conversation now and carries on from the summary; it can't run while the agent is working. If a command is refused, the reason shows above the box. Text starting with "/" that isn't a command is sent as a message.
- {{User}}'s messages are bubbles on the right in the agent's color. The conversation grows with the window, up to about twice a comfortable reading width. It also shows the agent's replies, its thinking, its tool calls (the calls one reply made share a block; each says on its row what it does, such as the command it runs with "+N lines" when there's more or the file it reads, and at the end how long it has run, ticking (for a command, also when it times out: "1m 23s · times out in 8m 37s", or "no limit" in the background), and once it's done, how long it took; click a call to expand its input and output), compaction dividers, and notices such as errors. An extension's tool calls show what they did with its icon, in a line and the details under it: a message sent ("→" the recipient, then the message, and Sent, or Queued when the recipient was working), the checklist items added or updated with their status and owner, a note read or remembered with its text, a monitor's name and when it fires, a background task's command and whether it still runs, the file shown, a search's results and the page read, a database query's SQL and row count, a secret given to agents or taken back, and the error when one failed. A message, a note or a monitor's prompt shows its first line, with Show more to read it all. The recipient opens their conversation, the file brings its pane forward, and a result or page opens in the browser.
- An agent's proposal to Rivet shows in its conversation as a card in Rivet's color: the proposal, a box for a comment, and **Approve** (or Enter in the box) and **Dismiss**. Approved, Rivet gets your comment and the proposal as your message; if it can't (no Rivet, or Rivet has no model), why shows on the card and the proposal waits. Decided, the card says Approved or Dismissed, when, and your comment.
- Events, the messages that didn't come from {{user}}, never look like theirs. A message from another agent comes in on the left in a bubble of that agent's color, under its character and name. Click its name or the bubble to open that agent's conversation (a drag or double-click in the bubble selects text instead); a sender that no longer exists isn't clickable. Queued messages from agents work the same. To go back, click the chip at the left of the header ("← Coordinator", naming the agent you came from), press ⌘[ or the mouse's back button; ⌘] or the forward button goes forward again, as in a browser. Agents deleted meanwhile are skipped. Picking an agent or project in the sidebar, Settings or the Marketplace starts over; the way back isn't kept, and each window has its own. Claktory's own notes (such as "Claktory restarted") and finished background tasks are a single centered line; click it to see all of it, such as the task's output.

- Panes: beside its conversation, an agent's main area can show files: text with line numbers, to select and copy (Markdown formatted, with Plain to see its source; a very large file shows its first 2 MB) and images (fitted to the pane; zoom with − and + in the header, ⌘+ and ⌘− once clicked, ⌘-scroll or a pinch; double-click for 100% and again to fit, or Fit, 100% and ⌘0). An empty file, an image too big to open (over 20 MB) or one that can't be read says so. A file opens there when the agent shows it to {{user}}, or when {{user}} clicks it in the explorer; one already open glows instead. With more than the conversation, each pane has a header with its name: drag a header onto another pane's top, bottom, left or right edge to split that pane equally, drag the line between two panes to resize them (double-click it to share equally again), and close a viewer with its × (the conversation can't be closed). Settings, the Marketplace and What's new open as panes too, right of the conversation, sharing its room, and move, resize and close like any other; they're never narrower than a phone's screen, and scroll sideways when squeezed. Up to 12 panes. The layout is kept by Claktory, the same on every device. On iPhone one pane shows at a time: open files are listed first under ⋯, and one opens over the conversation.

### Extension bar and panels
- A thin bar right of the sidebar has an icon for each extension turned on for the selected agent; hover one for its name. It changes as you click other agents.
- Clicking an icon opens that extension's panel on the right of the window; clicking it again, or the panel's ×, closes it. Each agent keeps its own panel open or closed, as you left it: switching agents shows that agent's panel. While a panel is open in a focused project it takes the explorer's place; closing it brings the explorer back.
- Drag the panel's left edge to make it wider, up to 800 points, or a little narrower (280; 320 by default), as far as the conversation keeps its room; double-click the edge to go back to the default. Like the sidebar's, the width is kept in Claktory, the same on every device and for every panel.
- **Checklist** panel: the agent's checklist of everything it was asked to do, like a chat. Above is the history: done and dropped items under the day each was added, oldest at the top, every day back; each day's heading says how much of that day's is done. At the bottom, **Outstanding** holds everything still to do, in progress first, then blocked (waiting on {{user}} or something outside, with what it's waiting on under it), then open, each oldest first, with the day it was added; when an item is done it moves up into its day. The top says how much is done overall. Each item shows its number, status (open, in progress, blocked, done, dropped) and owner; click an item to see its log of updates. It opens at the bottom and follows it as the agent changes things; scroll up and it holds still, with a round arrow button to jump back to the latest. It's read-only in the app.
- **Messaging** panel (the people icon): who the agent can message, and who can message it, each agent with its character, name, its project when it's another one ("Admin" for an admin agent such as Rivet, "Workspace" for another agent in no project), and, lined up at the right, whether it's working, idle or has no model, live. Each list says when it's empty (and, when other agents can't message it, that it's turned off in its settings). Change who can message whom in the agent's settings, under Extensions.
- **Memory** panel (the brain icon): what the agent remembers for itself. **Preferences** lists its rules by number, each with why and when it was learned (and changed); **Notes** lists its notes by name and summary, and clicking one opens the note; **Recent changes** says who changed what and when, newest first. It updates live as the agent writes it, and is read-only in the app. The **Claktory manual** (the open book icon; Memory's "factory" instance, on for admin agents) opens the same way, read-only: just its notes, the parts of this manual kept there, each opening to its text.
- **Tasks** panel (the terminal icon): the agent's background tasks (every agent's, with whose each is, when it sees all of them): **Running** first, then **Finished** in the last day, newest first. Each shows its command, its id, when it started, how long it has run (ticking) or ran, and how it ended ("exit 0", "timed out", "stopped by {{user}}"; failures in red). Click one to see the last lines of its output and where its log is. **Stop** on a running one stops it (its whole process group), and the agent gets the usual event that it finished, "stopped by {{user}}". It updates live.
- **Monitors** panel (the alarm clock icon): what will prompt the agent later. **Active** monitors first, then **Paused** (paused, or failed: "Failed: its command kept failing", in red), then **Ended** in the last week. Each shows its name, what it waits for ("every 1h", "check `make test` every 5m, fires on failure"), its number, when it next fires (counting down), when it last fired and how many times, and its end ("until …", "2 of 5 fires") when it has one. Click one to see the prompt it sends and who set it. **Pause** or **Resume** and **Cancel** change it as you; if that isn't possible now, the reason shows under it. Under them, **Also wakes it** lists what else will wake the agent, such as a running background task. It updates live.
- **Database** panel (the database icon): the agent's database, read-only. At the top, where its file is; then its **Tables** and **Views** by name, each with how many rows it holds. Click one to see its columns and their types. It's empty until the agent makes tables. **Claktory's records**, admin agents' view of Claktory's own records (`factory.db`, without agents' memory), shows the same way, under its own database icon.
- **Resources** panel (the gauge icon): how the machine and Claktory use its resources, sampled every minute. At the top, any alerts in effect (what admin agents were told, in red). **Machine**: processors (how busy, of how many cores), memory and swap used, and each volume Claktory uses with its free space and what of Claktory's is on it; a gauge past its alert's threshold (Settings → Resources) is red. **Last hour**: memory and processors as small lines, with the latest value. **Claktory**: its own processes (backend, supervisor, app) and the agents' background tasks, monitors' watches and commands running now, each with its agent, how busy it keeps the processors (100% is one core) and its memory. **Other processes**: the machine's biggest others by memory. **Disk** (measured every 20 minutes, with when): Claktory's data, its releases, each agent (click one for its conversations, logs, database and checkout) and each project's folders, with the build caches in each agent's checkouts and each project's folders listed among its parts, each with **Clean**, which clears it now (a build fills it again; it's refused while an agent works there or a build runs in it, saying why). Checkouts are copy-on-write: they share most of their blocks with the checkout they were made from, so they take less than they're counted as. A size Claktory couldn't finish measuring says "at least". Otherwise read-only.

<!-- admin: app-marketplace | The Marketplace: agent templates, skills and extensions. -->
### Marketplace (the bag at the bottom of the sidebar)
- Three kinds of things to add to Claktory: **Agent templates** (ready-made agents: a prompt, a model and the skills they come with), **Skills** (know-how an agent can pick up for one kind of task; templates come with theirs, and any agent can be given more) and **Extensions** (new capabilities for Claktory itself, added while it runs).
- **Extensions** lists the extensions Claktory has, with what each does and whether agents get it unless it's turned off (Messaging) or only once turned on (Checklist). Turn one on or off for an agent in that agent's settings. Nothing is offered under Agent templates or Skills yet.

<!-- admin: app-settings | The Settings screen: your name, providers, defaults, devices, display; the first launch's name question. -->
### Settings
- The first time the app opens with no name set, it asks "What's your name?" over everything; agents call the person by it. It's the backend's, so it's asked once, on any device.
- **General:** **Your name**, the first name agents call you by.
- **Providers:** every model provider and the accounts Claktory is signed in to with it, subscriptions and API keys, in the order requests use them (see Models and signing in), each with its plan, its usage and whether it's in use, at its limit until when, or out of credit; each subscription by its email, each key by its name or its end ("sk-…a1b2"); before any account, buttons to sign in, and after, **Add another Claude subscription** (or ChatGPT) and **Add an API key**, which add an account and never replace one; drag an account by its grip, or click **Use first**, to change the order; **Rename** a key (an empty name goes back to its end); a key out of credit says so, links to the provider's billing page, and has **Try again**; and **Sign out** of each. A key from the environment shows last and can't be moved, renamed or signed out of. Hovering an account's circle shows its limits.
- **Defaults:** the model and effort new agents get, and the compaction threshold.
- **Devices:** the devices that can show this Claktory, each with when it last connected and when it was added (the one in hand marked "This device"), and Remove (for this device, after asking); and **Add a device…**: name the device ("iPhone") and its code shows, once, as a QR code to scan with Claktory on an iPhone, with Copy code to paste it on another Mac. Adding a device turns on access from other devices; there's no port or address to set. On a device showing a Claktory elsewhere, "This device" says whether it's connected, and if it can't connect, what to do.
- **Resources:** when admin agents with the Resources extension, such as Rivet, are told the machine runs low: memory used above a percentage (90 unless changed), a volume with less free than so many GB or a percentage of it, whichever is smaller (10 GB, 10%; 0 GB turns it off), and the processors busier than a percentage (off unless set; 0 turns it off); and **Build caches**, how big each agent checkout's or project folder's build caches may grow (25 GB unless changed; over it, Claktory clears them while nothing works there; 0 never). Type a number and Save.
- **Secrets:** the vault's secrets and who has each (see Secrets).
- **Display:** the **Highlights** switch (on unless turned off).

### Highlights
- A soft glow fades in and out on what changes, so you see it happen: a new agent (in its color), project or folder in the sidebar; a checklist item that's added or changes status in the Checklist panel; both agents' rows, in both their colors, when one messages another; and whatever an agent points out with its highlight tool, with what it says in a small note beside it that goes after a few seconds or on a click. - Turn them off in Settings → Display; then nothing glows.

### Map
- The Map draws how this Claktory is arranged, so {{user}} can spot an agent that shouldn't have something and plan changes. Claktory works it out from the same rules agents follow; the app only lays it out, and it changes as soon as the settings or the vault do.

## Agents

- An agent is persistent: one conversation that continues across messages, days and restarts. It doesn't start fresh each time.
- Every agent is the same coding agent. What makes one different is its **name** (its identity, often a human first name such as "Mike"), its **role** (what it does, such as "Coordinator", shown with the name; optional), its **prompt** (instructions added to its system prompt), its **model**, its **effort** (how hard the model reasons), and its **project**.
- **The user's name:** the person agents work for can give their first name (asked when the app first opens, and in Settings). Every agent's system prompt then names them ("The person you work with is Lee."), and Claktory's own texts and events use it ("Lee approved your proposal to Rivet"); without it, they say "the person". A new name reaches agents already working as a short note from Claktory, and their system prompt says it from their next context.
- An agent's prompt can use the manual's placeholders: `{{user}}` and `{{User}}` become {{user}}'s name (or "the person" and "The person" without one), and `{{home}}`, `{{config}}` and `{{workspace}}` this Claktory's folders. They're filled in when its system prompt is written, and the prompt keeps them as written.
- Changing an agent's model, effort, prompt, name, role, project or folder applies from its next step (its next model call), even in the middle of a task, and the agent is told in a short note from Claktory ("Your model is now …", "Your instructions changed; the new ones are in your system prompt from now on.").
- An agent works in its project's folder, or in the workspace folder `{{workspace}}` when it's in no project. Its tools read, write and edit files and run shell commands.
- In a project with **folders** (see Projects), an agent works in one of them, or in the project's own folder. Its shell starts there, and write_file and edit_file change files only there; it can read the whole project, every folder of it. bash can't be held to its folder, so the agent is told to change files only in its own, with bash too. Its system prompt lists the project's folders, which one is its own, and the rest as read only.
- When an agent's context reaches the compaction threshold (400,000 tokens unless changed), Claktory summarizes the conversation and the agent continues from the summary. A divider marks the spot.
- An agent left idle with a long conversation is also summarized just before its model's prompt cache expires, so {{user}}'s next message after a long break doesn't pay to cache the whole conversation again: after 54 minutes when Anthropic's "Keep conversations ready" (Settings → Providers) is 1 hour, or after 4 when it's 5 minutes (the default) and "Also after 5 minutes idle" is on. Only for a conversation of at least 150,000 tokens (on a 200,000-token model; 75% of a smaller window, at most 200,000 on a larger one), once until the agent works again, and only on time: a check that comes late (the machine slept) lets it be. It doesn't run the agent: nothing new shows, and a message or Stop meanwhile cancels it and leaves the conversation as it was. The divider says it was summarized while idle. Claktory can't choose or know how long other providers' caches last, so their agents are never summarized while idle. "Summarize idle conversations" (Settings → Defaults) turns it off.
- **Slash commands** are for {{user}}, typed in an agent's message box: `/clear` stops the agent (as Stop does, but dropping queued messages) and starts it on a new, empty conversation, so it works with no history (no bias from earlier, fewer tokens). The old conversation is archived in the agent's folder, not shown in the app; its checklist and memory stay. `/compact` summarizes an idle agent's conversation now, as if it had reached the threshold. Agents can't run commands, on themselves or others.
- Models suit different jobs: a strong reasoning model for building software, another for writing that should sound human. Each agent picks its own.
- Every agent has a **color**: blue, violet, green, pink, teal, amber, red or slate. Unless {{user}} picks one, a new agent gets the color that looks least like any agent's color, so agents are as easy to tell apart as possible (after Rivet's blue: red, green, slate, pink…). Once all eight are taken, the one fewest agents have.
- **Events** prompt an agent the way a person's message does, but come from somewhere else: another agent, a background task that finished, one of its monitors, or Claktory itself (after a restart, say). An event wakes an agent that's idle; a working agent gets it as soon as its current step ends (its model reply, or the tool call it's running), and reads it before going on. The model reads an event wrapped in an `<event source="…" from="…">` tag; a message from an agent is signed with its name and role (`from="Mike (Coordinator)"`), and from an agent in another project names that project too (`from="Ana (Frontend, Web Site)"`), or says it's from an admin agent (`from="Rivet (Admin)"`, or `from="Rivet (admin)"` with no role), and the tag gives the sender's `id` when its name doesn't.
- **Where {{user}} writes from:** each of {{user}}'s messages reaches the agent wrapped in a `<sent from="…" device="…">` tag: the device they sent it from (a paired device's name, or this computer's for its own app) and its kind, `desktop`, `laptop`, `phone` or `tablet` (left out by apps that don't say). Agents fit their replies to it: on a phone, short and to the point, without long code or tables; at a desktop, as full as the work needs. The app marks each of {{user}}'s messages with a small glyph for its device; hovering it, or touching and holding it on iPhone, shows the device's name.
- **Agents message each other** with the Messaging extension (see Extensions): `agents_send` by id or name (or role, when just one agent it can message has it), or to several at once with a list (up to 20: the same text to each, each told who else got it, as "Also sent to: Lena (Backend), Omar (Backend)." at its end), and `agents_status` to see who's idle or working. Agents see each other's roles with their names, everywhere: in `agents_status`, in the list of agents they can message (`Mike (mike, Coordinator)`) and in how messages are signed. The message reaches the other agent as an event from the sender, and replies come back the same way. This is how agents work together, such as a coordinator handing work to a frontend agent and a backend agent.
- **Who can message whom:** an agent sees and messages only the agents in its own project (agents in the workspace are a group of their own), plus any its `also` list grants. An admin agent sees and messages every agent. An agent that isn't reachable, or has the Messaging extension off, can't be messaged by anyone, and others don't see it at all. Grants go one way: for two agents in different projects to talk both ways, each needs the other in `also`. The Map in the app draws all of it, with the secrets and data each agent has. Each agent's system prompt lists the agents it can message as they were when its conversation (or its context, since the last compaction) began; when that changes, Claktory tells it before its next step ("You can now message: Designer (designer)."), and the same for the models available.
- **Proposing to Rivet:** no agent can message Rivet, but one that reaches a conclusion Rivet should act on (the backend agents are saturated, so another is needed) proposes a message for it with `propose_to_rivet`, written to stand alone. The proposal shows in that agent's conversation, where {{user}} approves it, with a comment if they like, or dismisses it. Approved, Rivet gets it as {{user}}'s own message: their comment, then "<Agent> (<role>) proposes:" and the proposal. Either way the agent is told, in an event from Claktory.
- **Names can repeat** across projects. Agents tell them apart by id: a new agent whose name is another project's agent's id gets an id with its project in front (`app-frontend`). Sending by name picks the agent in the sender's own project; when that doesn't settle it, the sender is told the ids to choose from.
- **Showing files:** to show {{user}} a file (a report, a chart, a screenshot), agents use `show` (Viewer extension), which opens it in a pane beside their conversation in the app, on whatever device {{user}} is using, instead of opening an app such as Preview on this machine.
- **Background tasks:** bash's `run_in_background` starts a long command (a server, a long build or test run) and returns at once with a task id. Its output goes to `{{home}}/agents/<id>/tasks/<task>.log`, and when it ends, the agent gets an event with its exit status and the end of its output. Tasks run on their own: a restart of Claktory's backend (an update, say) doesn't stop them, and the agent still gets the event when one ends. A command not run in the background gets 2 minutes (`timeout`, up to 10); one still running then moves to the background and runs on as a task, for up to 30 minutes more, and the agent gets its event when it ends, with a note to make it faster or start it in the background next time (a command that starts with `sleep` is stopped instead). A message moves a running command to the background the same way, so the agent reads it sooner: {{user}}'s at once, another agent's once the command has run a minute (task and monitor events wait for it to end). A background task is stopped after 30 minutes unless its `timeout` asks for longer, up to 2 hours. Every result and task event says how long the command took ("[exit 0, 4.2s]"). Output up to 30,000 characters comes back whole; longer output gives its start and end and the path of its whole log. Two mistakes are refused before they start, with what to do instead: a command that begins by sleeping 25 seconds or more (outside the background), since events wake the agent anyway, and one that copies a repository the agent works in or reads (`cp -R`, `ditto`, `rsync`, `git clone`, `git worktree add`), which Own checkout or `git archive` does better. When a task has run 24 hours (`task_alert_hours`), the admin agent (Rivet) is told, once.
- **Rivet** is the agent every Claktory starts with, in the workspace. Rivet helps {{user}} achieve what they want with Claktory: it sets Claktory up for their goals (projects, agents, prompts, models and settings), answers questions about Claktory and changes it for them. When {{user}} clicks a "+" in the sidebar, their request reaches Rivet as their own message, starting "Set up a new project for" or "Add an agent to <project> that": Rivet sets it up as asked, with a prompt, model and extensions that fit. Rivet is the **admin agent**: it sees and messages every agent, in every project, and no agent can message it, because it hands out work rather than hearing back. Otherwise Rivet is an ordinary agent with its own prompt; it can be renamed, changed or deleted like any other. Its prompt is Claktory's default until someone edits it, and a default follows each new version of Claktory: an update brings the newer default; an edited prompt stays as it was. Rivet's settings can reset it to the default. Its role is "Admin". Every agent Rivet creates gets a human first name, picked at random and different from the names of the other agents in its project, and a short role that says what it does.

## Extensions

Extensions are capabilities an agent has on top of its coding tools. Each is on or off per agent, with its own options; an agent with one on gets its tools and a short section in its system prompt saying how to use them. Turning one on or off, or changing its options, reaches the agent as a note before its next step, since its system prompt and tools stay as they are for the whole context so it stays cached. An extension turned on works from that step: the note brings its instructions and its tools, which the agent calls through its tool `extension_call` (`tool`, `args`) until its next context (after a compaction, or /clear) puts them in its tool list and system prompt. A turned-off extension's tools are refused at once. A new version of Claktory that brings an extension on by default says so the same way.

Claktory's extensions are Messaging, Checklist, Database, Memory, Monitors, Resources, Secrets, Tasks, Highlights, Own checkout, Viewer and Web. An extension can also have **instances**, named second uses of it that are on or off on their own: the Claktory manual (`memory:factory`) is the Memory extension's, a read-only memory holding the rest of this manual (the app screen by screen, every extension, the settings file, signing in, where Claktory keeps things). Admin agents such as Rivet have it unless it's turned off, and any agent can be given it; it opens a note with memory_read as it needs it. Claktory's records (`database:factory`) is the Database extension's: factory.db to read with SQL, for admin agents the same way.

- **Messaging** (id `agents`; on unless turned off): messaging other agents and seeing their status. Tools: `agents_send` (`to`: an id or name, or a list of up to 20; `text`. With a list, the sender and repeats are left out, one it can't message doesn't stop the others, and the result says for each whether it was sent, read after its current step, or why not; reaching none fails) and `agents_status` (every agent it can message, one line each: id, name, project if not its own ("admin" for an admin agent, wherever it is), idle or working and for how long, the tool it's running, queued messages, "no model"; or just `agent`), with `see_map`, `agents_map` (who can message whom: one line per agent, whom it messages and by whom it's messaged; or just `agent`), and for agents that aren't admins, `propose_to_rivet` (`message`: what Rivet should hear, standing alone). A proposal returns at once ("Proposed; {{user}} will approve or dismiss it.") and shows in the agent's conversation as a card for {{user}}, kept across restarts; with no admin agent, or one whose model can't run, it says so and proposes nothing. Proposals go to the agent with Rivet's id if it's an admin agent, else to the first admin agent in the settings. Approved, Rivet gets it as {{user}}'s message (their comment, a blank line, "<Agent> (<role>) proposes:", a blank line, the proposal; the role is followed by the agent's project when it's in one); approving waits while Rivet has no model. The agent gets a Claktory event either way: "{{User}} approved your proposal to Rivet (comment: …)." or "{{User}} dismissed your proposal to Rivet.", with the proposal below it. Options: `reachable` (other agents can message it; on unless turned off), `admin` (it sees and messages every agent, and sees the map; Rivet's is on), `see_map` (it gets `agents_map`) and `also` (agents outside its project it may also message). Its panel shows whom the agent can message and who can message it.

- **Checklist** (off unless turned on): the agent keeps everything {{user}} asks for as a checklist and works through it over days, so nothing is forgotten. Each item has a number (#1, #2…), text, a status (open, in_progress, blocked, done or dropped), an owner (an agent, or none) and a log of what happened to it. in_progress means someone is on it right now; blocked means it waits on {{user}} or something outside, with a note saying on what. Tools: `checklist_add` (many items at once), `checklist_update` (status, owner, text and notes, for several items at once), `checklist_list` (outstanding items, open, in progress and blocked, unless asked otherwise; filters by status, day added, owner or text; `agent` reads another agent's checklist) and `checklist_item` (one item's history). Option: `nudge` (on unless turned off): when the agent has been idle a little while with open or in-progress items, and nothing will wake it (no message waiting, no background task running, no agent working that owns one of its items), Claktory reminds it once, listing them; it isn't reminded again until something changes (an item, a message for it, an owner working). {{User}} sees it in the agent's Checklist panel.
<!-- admin: ext-database | Database extension: the agent's own SQLite database, its tools and limits, and Claktory's records (database:factory). -->
- **Database** (id `database`; off unless turned on; its instance **Claktory's records**, `database:factory`, is on for admin agents unless turned off): a SQLite database of the agent's own, for structured data it collects or keeps track of over time (records, lists, results) and wants to query rather than reread. No agent has one by default: Rivet turns it on for agents that produce data, or that oversee projects producing data, to hold their metadata, so it has a good interface: SQL for the agent, and the Database panel for {{user}}. It's `{{home}}/agents/<id>/database.sqlite`, made on the agent's first write; it lasts across compactions and /clear, and goes when the agent is deleted. Tools: `db_exec` (`sql`, `params` filling ?1, ?2…: CREATE TABLE, INSERT, UPDATE, DELETE; several statements at once without params, applied all or none), `db_query` (one SELECT; a header line and up to 200 rows, cells joined with " | ", and how many more there were) and `db_schema` (its tables and views with their columns and row counts, or with `table` one's CREATE statement and indexes). A call runs at most 10 seconds and a database holds at most 1 GB; ATTACH and loading SQLite extensions are refused. With **Claktory's records** on, `db_query` and `db_schema` read Claktory's own records, factory.db (with `instance: "factory"` when the agent has its own database too; see "Where Claktory keeps things" for its tables): read only, and without the agents' memory (the `memory_` tables), which stays each agent's own even from admin agents. {{User}} sees an agent's tables in its Database panel, and Claktory's records in the Claktory's records panel.
<!-- admin: ext-memory | Memory extension: preferences and notes, caps, what goes in the prompt, its tools. -->
- **Memory** (off unless turned on; its instance **Claktory manual**, `memory:factory`, is on for admin agents unless turned off): the agent's own memory, kept across compactions and never shared with other agents. Turn it on for agents that should learn {{user}}'s ways, such as a lead who keeps proposing things. **Preferences** are what {{user}} wants and doesn't, each with why ("Don't propose paid CI. Why: everything runs locally."), numbered #1, #2…; the agent adds one when corrected for a general reason and replaces it rather than adding near-duplicates. **Notes** are what it learned about how things work, each with a short name (slug), a one-line summary and a body. The agent's system prompt shows its preferences in full and its notes' summaries, as they were when its context began (fixed until the next compaction, so the cache holds); changes since are in its conversation. Memory is capped: preferences at 16,000 characters in all, notes at 100. Tools: `memory_update` (several changes at once, all or none: add, replace or remove preferences; write, edit or remove notes) and `memory_read` (`note` opens one, `q` searches, nothing shows preferences and notes' summaries as they are now). {{User}} sees it in the agent's Memory panel.
<!-- admin: ext-monitors | Monitors extension: kinds of monitors, limits, repeat, what a fire says, its tools. -->
- **Monitors** (on unless turned off): prompts that wake the agent later. A monitor is a prompt the agent writes plus what it waits for: a time (`at`, or `in` "45m"), an interval since its last fire (`every`), a cron schedule in local time (`cron`), a command it runs every so often succeeding, failing, matching a regex or changing its output (`check`), files or folders changing (`files`), or a long-running command printing lines, all of them or ones matching a regex (`watch`). When it fires, the agent gets its prompt as an event from the monitor (`<event source="monitor" from="<name>" id="m3">`), with what happened (the check's output, the files that changed, the lines printed). Monitors are numbered m1, m2… per agent and last across restarts, compactions and /clear until they're done or cancelled; stopping the agent doesn't pause them. A monitor can end on its own (`until` a time, `max_fires`); a check fires once unless `repeat` is true (each time its condition becomes true again) or "always" (at every check where it holds), and its command gets `FACTORY_MONITOR_LAST_FIRED` (unix seconds of its last fire, or of when it was added). Time monitors wait until the agent is idle (`idle_only`) unless told otherwise. They can't flood an agent: a monitor never has more than one fire waiting, and what happens meanwhile comes with that one; every kind has a shortest period (a minute for times, 30 seconds for checks); an agent has at most 20 active monitors, 5 of them watches; and when an agent's monitors fire 30 times in an hour, the one going over is paused, with one notice. A check that can't run 5 times in a row, or a watch whose command keeps exiting at once or whose output passes 50 MB, stops with an error. Tools: `monitors_add` (several at once, all or none; `agent` sets one for another agent it can message), `monitors_list` (its monitors one line each, and what else will wake it: running background tasks, the checklist reminder; `all` adds those that ended in the last week) and `monitors_change` (pause, resume, cancel, or fire now to try the prompt). A watch's output goes to `{{home}}/agents/<id>/monitors/m<n>.log`. An agent a monitor will wake soon isn't reminded of its checklist.
<!-- admin: ext-resources | Resources extension: the machine's and Claktory's processors, memory and disk, the resources tool, and the low-memory and low-disk alerts. -->
- **Resources** (id `resources`; on for admin agents such as Rivet unless turned off, off for others unless turned on): how this machine and Claktory use its processors, memory and disk, for the agent to look into and tell {{user}} about. Claktory samples the machine every minute and keeps the last hour; what its data and projects take on disk is measured in the background every 20 minutes. Claktory's own processes are told apart by process group: its backend, supervisor and app, each agent's background tasks and monitors' watches, and the commands agents are running now; everything else is grouped by app or program name. Tool: `resources` (a few lines: processors, memory, swap and each volume's free space, Claktory's processes, the other programs using the most memory, alerts in effect; `detail`: `processes` for every one of Claktory's process groups and the top others, `disk` for each volume and what Claktory's data (releases, each agent's conversations, logs, database and checkout), and each project and folder take, with their build caches, or `history` for the last hour every 5 minutes; `clear_cache`: a build cache's path, to clear it now when {{user}} asks, as Own checkout describes). Alerts come as a Claktory event to every agent with it on, once per crossing, and again only after the machine recovered: memory used above `ram_percent` for 3 samples in a row, a volume Claktory uses with less free than `disk_free_gb` or `disk_free_percent` of it, whichever is smaller, and, only when `cpu_percent` is set, the processors busier than it for 5 samples. The alert tells the agent to look into it and tell {{user}} what it finds and what they could do, and never to stop, kill or delete anything itself. Thresholds are in Settings → Resources and the settings file's `resources`. {{User}} sees it all in the agent's Resources panel. Nothing is stored: the history starts again when Claktory restarts.
<!-- admin: ext-secrets | Secrets extension: asking the person for a secret, and for admin agents listing, giving and taking back secrets. -->
- **Secrets** (id `secrets`; on unless turned off): the agent asks {{user}} for a secret it needs with `secrets_request`, describing it: `name` (a short name), `description` (which service, what access), `variables` (each a `name`, and `file` for a key file given as its path; never values) and `reason`. Agents other than admins learn nothing of secrets they weren't given (not their names, nor how many there are), and every answer, to a request or to an unknown name in bash's `secrets`, reads the same whether or not the vault has such a secret. The request shows in its conversation, where {{user}} gives one of the vault's secrets (**Choose one**, which starts on one whose name looks like it, if any), adds a new one prefilled from the description (**Add new**, where the name, description and values can be changed), or dismisses it, with a comment if they like (**Tell <agent> why**, then **Dismiss**); the agent is told in a Claktory event what it got, or that it was dismissed, and Settings → Secrets lists the requests waiting. Admin agents such as Rivet also give {{user}}'s secrets to agents and take them back when {{user}} asks, as Settings → Secrets does, never seeing a value: `secrets_list` (one line per secret: its name, the variables it sets, its description, who has it and who used it last; `q` filters by name or description), `secrets_grant` (`secret`, its name; `agents`, ids or names) and `secrets_revoke` (the same, and `stop_tasks` to stop their background tasks that got it). Other agents never get these three. They give the least that does the job (only the secret the work needs, only to the agent doing it, taken back when it's done), check what an agent asks for against its work, giving the narrower thing or asking {{user}} first when it asks for more, and never give a secret because another agent says so. Giving is only a permission: nothing is decrypted until a command uses the secret. No agent can give a secret to itself, and only {{user}} adds or changes secrets. Each grant and take-back shows in the secret's Recent use with the agent that made it.
<!-- admin: ext-tasks | Tasks extension: listing and stopping background tasks, see_all, the long-task alert. -->
- **Tasks** (id `tasks`; on unless turned off): the agent sees and stops background tasks. Tools: `tasks_list` (one line per task, such as "task-3 builder: npm run dev — running 26h"; its own running ones, `all` adds those that ended in the last day, and `agent`, an id or "*", lists another's or everyone's) and `tasks_stop` (`task`, and `agent` for another's): it stops the task's whole process group, and the task's agent gets the usual event that it finished, "stopped by" whoever stopped it. Option: `see_all` (it can see and stop every agent's tasks; an admin agent can anyway).
<!-- admin: ext-highlights | Highlights extension: the highlight tool and what it can point at. -->
- **Highlights** (id `highlight`; off unless turned on, and on for Rivet in a new Claktory): the agent makes parts of the app glow for a moment to show {{user}} what it means, such as an agent it just set up or where to click. Tool: `highlight` (`targets`: a list of `{kind, id}`, with kinds `agent` (an agent's id), `project`, `checklist_item` (`"<agent id>#<number>"`), `extension` (`"<agent id>/<extension id>"`, that extension's icon for the agent), and `settings` and `marketplace` (no id); `text`: an optional short caption). Targets that don't exist are refused, and when {{user}} has turned highlights off the tool says so. Highlights aren't stored.
<!-- admin: ext-own-checkout | Own checkout extension (tree): an agent's own git checkout and branch, tree_land, when checkouts are made and removed. -->
- **Own checkout** (id `tree`; on unless turned off): the agent works in its own checkout of its project's git repository, on its own branch `factory/<agent id>` (a Claktory in another home folder names its branches after it, such as `factory-dev/<agent id>`, so two Claktories never share one), so agents working in parallel don't step on each other's edits and builds. An agent whose folder isn't in a git repository works there as before (its system prompt says why it has no checkout). Turn it off for an agent that should work in the main checkout itself, such as one that builds releases from it. Before the agent's first run with it, Claktory makes the checkout (the agent's conversation says so, and the agent starts once it's ready) in `{{home}}/trees/<agent id>/<repository folder name>`: the files git tracks, as they are in the branch, copy-on-write where the disk allows (APFS on a Mac, btrfs or XFS on Linux), so it takes almost no space; elsewhere, or on another volume, git writes them. Nothing git ignores comes along (build output such as `target/` or `node_modules/`, local settings), so making one takes moments however big the build output is, and the first build in it is a full one. The agent works in the same place in it as in the project, may read the main checkout but not change it with its file tools, and keeps the checkout across days. It commits there, rebases onto the main branch, and lands its work with the tool `tree_land`, which fast-forwards the main checkout's branch to its branch (refused, saying why, if the main branch moved on or changes there would be overwritten). When the agent is deleted or the extension turned off, its checkout and branch are removed, unless it has uncommitted changes or commits not landed: then they're kept. Agents never make git worktrees or copies of a repository themselves; this is how an agent gets a checkout of its own. **Build caches stay bounded:** every 10 minutes Claktory looks for build caches in each agent's checkout and in each project's folders (the main checkout included), whether or not the agent has Own checkout: only folders known to be build caches, a `target/` beside a Cargo.toml, a Flutter `build/` or `.dart_tool/` beside a pubspec.yaml, a Gradle `build/` or `.gradle/`, `node_modules/`, `.next/`, `.turbo/` or `.parcel-cache/` beside a package.json, a Swift `.build/` beside a Package.swift, or any folder tagged as a cache (CACHEDIR.TAG), up to four folders deep, and never one git tracks a file in. Nothing else git ignores (.env files, local data, a `build/` that isn't a build's) is ever touched. First, where nothing works, it deletes the object files Rust builds leave behind (`*.rcgu.o` in a `target/`'s `deps` folders, older than 3 hours): on macOS, Rust 1.88 and later leaves a new set at every rebuild and never deletes the old ones (rust-lang/rust#161824), about a GB per test run of a large project, and cargo still finds everything up to date without them, so nothing rebuilds and no one is told. Then, when one checkout's or folder's caches together still take more than the budget (`resources.build_cache_gb`, 25 GB unless changed, in Settings → Resources), and nothing works there (its agent, or for a project folder every agent whose tools start in it, isn't running and has no background task or watch running), Claktory clears them, largest first, until they're under it, leaving any written in the last 5 minutes or with a Rust build holding its lock: each is moved aside at once (to `{{home}}/trash`, or beside it with a name starting `.factory-trash-` on another volume) and deleted in the background, and it's logged. The agents working there hear of it at their next run, in a Claktory event ("Your checkout's build cache (N GB, path) was cleared; the next build is cold."). One cache can also be cleared on request, by {{user}} in the Resources panel or by an agent with the resources tool's `clear_cache`, on the same conditions. The dev Claktory (`~/.factory-dev`) looks only inside its own data folder, so it never clears caches in a project folder elsewhere, such as a repository the real Claktory's agents build in.

- **Viewer** (id `viewer`; on unless turned off): the agent shows {{user}} files in the app. Tool: `show` (`path`: absolute, or relative to the agent's working folder; `kind`: `text` or `image`, inferred when left out: an image the app shows (PNG, JPEG, GIF, WebP, BMP) by its content, else text if it's UTF-8; anything else is refused, saying why). It returns at once ("Showing <path> to {{user}}."): the file opens in a pane of the agent's main area, right of its conversation, stacked below any viewers already there; a file already open isn't opened again, and its pane glows instead. A layout holds at most 12 panes; past that, a new file takes the first viewer's place. Each agent's layout is kept in factory.db (`layouts`), the same on every device; {{user}} rearranges and closes panes in the app. The app reads files from Claktory's machine, text up to 2 MB and images up to 20 MB, so viewers work from another device too. PDFs, documents to edit together, dashboards and extension panels as panes are to come.

- **Web** (id `web`; on unless turned off): the agent searches the web and reads pages, as a browser on this computer would, with no account or key. Tools: `web_search` (`queries`: 1 to 4; `domains`: `example.com` keeps only that site, `-example.com` leaves it out; `recency`: day, week, month or year; `limit`: results per query, 8 unless asked, at most 10) gives each result's title, URL and snippet. `web_fetch` (`url`, and `offset` or `find`) reads a page (HTML, Markdown, text, JSON or PDF) as numbered Markdown lines, about 20,000 characters at a time; with `find` (several separated by `|`) only the matching lines, with the lines around them. Searches go to DuckDuckGo, and to Brave when DuckDuckGo can't answer. Every agent searches from the same computer, so searches are paced for the whole Claktory (a few seconds apart on DuckDuckGo, about 20 on Brave, each with an hourly budget). An engine that blocks (a CAPTCHA, a rate limit) isn't asked again for an hour or more; while none can answer, web_search says which and until when. Searches are kept for an hour and pages for 15 minutes, so asking again costs nothing. web_fetch reads only public pages, never this computer, its network or a bare host name; it follows redirects within a site and reports one to another site, for the agent to fetch if it wants.

## Projects

- A project is a folder in the workspace, named after the project: "Web Site" lives in `{{workspace}}/web-site`. Creating a project only asks for its name.

## Secrets

- Claktory keeps the keys and passwords agents use (an AWS key, a Cloudflare token) in its **vault**, encrypted on this machine. Only {{user}} adds secrets, in Settings → Secrets, and gives them to agents and takes them back there, or asks an admin agent such as Rivet to (Secrets extension). Agents never see a value, and other agents can't read the vault or give a secret to anyone.
- An agent sees only the secrets it was given: it finds them in its system prompt's "Secrets" section, each with the variables it sets, or hears of a new one in a Claktory event ("You can now use the secrets …"). To use one, it passes the secret's name in bash's `secrets` (`"secrets": ["Cloudflare"]`): that command, and the background task it starts, gets the secret's variables in its environment (one saved as a file gets the path of a file holding the value, removed when the command ends). A secret it wasn't given, or a vault that's locked, is refused with what to do.
- Values are hidden wherever an agent or the app could read them: in every command's output and tool result, in events, messages between agents and the Tasks panel, a value shows as `[secret NAME/VARIABLE]`. An agent never prints a value, writes one to a file or commits one; when it needs a secret it doesn't have, it asks {{user}} for it with `secrets_request` (Secrets extension), never in a message.

### Signing in to claktory.com

- Being tried out, and off unless `account.enabled` is true in the settings (`"account": {"enabled": true}`; `service` points it at another account service than claktory.com's, `https://` or `http://` on this computer only). ## Claktory on another machine

Claktory's backend can run on an always-on machine (a Mac mini, a Linux server) and serve the app on other devices, so agents keep working while the laptop sleeps or travels. Every device shows the same Claktory.
- Claktory reaches other devices through its **private tunnel** (iroh): every connection is encrypted end to end between Claktory's key and the device's, and goes directly between the two machines when it can (the same network, or a path punched through the routers), or else through a relay that passes it on without being able to read it. Claktory opens no port to the internet and asks the router for none; a device that isn't paired is turned away right after the encrypted handshake, before it sees anything of Claktory. It works from any network, with no VPN, account or port to set up. Access is on while a device is paired, or its code is waiting: adding a device turns it on and removing the last one turns it off. Relays are n0's (iroh's makers) unless the settings file names others (`remote.relays`); with your own, nothing goes to n0.
- Pair each device: in the app showing that Claktory, Settings → Devices → **Add a device…** makes its code, shown once as a QR code with Copy code; the list there shows when each device last connected, and Remove takes one's access away at once, closing its connection. Or on that machine: `{{home}}/bin/factoryd pair <device name>` prints a code, `factory://?t=…&name=…&e=…` (`e=` is Claktory's key; `r=` names a relay and `a=` an address, when there are any), once. It holds the device's token, so treat it like a password: the first device to use it binds its own key to it, and then it's useless to anyone else. A code nobody uses stops working after 10 minutes. `factoryd devices` lists paired devices and when each last connected; `factoryd unpair <device>` takes one's access away at once. Only the person, or an agent on that machine, can run these.
- On an iPhone: open Claktory and tap **Scan code** (or **Paste code instead**). On a Mac: click **+** at the bottom of the rail at the window's far left, paste the code under **Connect to another Claktory** and click Connect. The device remembers it, and the rail switches back to **This Mac**, or to another Claktory.
- This machine's own app connects through the tunnel too, on this machine only, with a code Claktory writes to `{{home}}/remote/local-pairing` (only that user can read it); access turning on or off never disconnects it. An app from before the tunnel still connects on the local port (7420) while an update is under way. Once this machine's app has connected through the tunnel, that port wants the token from `local-pairing` too, so nothing on the machine drives Claktory without it (scripts can use it). Devices paired before the tunnel can't connect: remove them and add them again.
- The agents run on that machine: projects, git credentials, tools and sign-ins live there, and a project folder's path is one of its paths: in project settings, type it, or click Choose… to browse that machine's folders (click a folder to open it; Up, Home and the path at the top move around; Show hidden shows folders starting with "."; Choose takes the folder you're in). Keep it awake. Sign in to providers there from the app by pasting the address or code the browser ends on. Web searches come from its address.
- A device elsewhere updates with the same Update banner: its app fetches the new app from that Claktory over the same encrypted connection (on a Linux machine, Claktory downloads the Mac release for it first), checks it, replaces itself and reopens, and Claktory's backend updates as usual. A release made before this, or one with no app, says why it can't update the app; the backend can still be updated.
- On Linux (x86_64 or aarch64, any distribution with systemd, NixOS included), Claktory runs as its backend alone, a single static program, with the app on a Mac or an iPhone. The same online installer as a Mac's, `curl -fsSL <channel>/install.sh | bash`, run as the person (not root), installs it as a systemd user service (`~/.config/systemd/user/factoryd.service`) that starts at boot, and shows a code for the first device, also as a QR code drawn in the terminal: scan it with Claktory on an iPhone, or on a Mac click Add a Claktory (+) at the far left of the window and paste it. `{{home}}/bin/factoryd pair "Device name"` makes a code for another device later, the same way. Starting at boot needs lingering (`loginctl enable-linger`), which the installer turns on when it may, and otherwise says to run `sudo loginctl enable-linger <user>`; on NixOS the configuration's `users.users.<name>.linger = true;` does it, and agents need `git` added to the packages. No port needs opening in its firewall. Updates come as on a Mac: the backend downloads them and the connected app offers them. Its log is `{{home}}/factoryd.log`.

## Models and signing in

Providers and how to sign in to each, all in Settings → Providers:
- **Anthropic:** a Claude Pro or Max subscription ("Anthropic (Claude Pro/Max)"), or an Anthropic API key.
- **OpenAI:** an OpenAI API key.
- **OpenAI Codex:** a ChatGPT Plus or Pro subscription, in the browser or with a device code.
- **OpenRouter:** an OpenRouter account in the browser, or an API key.

Subscription sign-in: {{user}} clicks "Sign in with …", the browser opens, they approve, and they're redirected back, which finishes it. If the browser runs on a different computer than Claktory's backend, or another program is using the port the redirect comes back to, the redirect can't arrive, so {{user}} pastes the address the browser ended up on (or the code it shows) into the box under the link. API keys are pasted into a hidden field.

**Several accounts:** a provider can be signed in to more than one account: several Claude or ChatGPT subscriptions, and several API keys beside them (keys carry credit to use). **Add another Claude subscription** (or ChatGPT), or **Add an API key**, signs in to another, kept beside the others (signing in again to one already there, or adding the same key again, just renews it; a plain sign-in replaces the first). A key is named by its end ("sk-…a1b2") until given a name; a key in Claktory's environment (ANTHROPIC_API_KEY, say) comes last, named by its variable. Requests go to the first account in the order that has capacity. When a subscription reaches its usage limit, Claktory skips it until the limit resets (as the provider says) and sends the request again at once to the next; when a key runs out of credit, it's skipped until it's tried again, by itself after an hour or when the person clicks Try again, and a request it answers shows it has credit again. The agent's conversation says so ("Claude account a@x.com reached its limit; continuing on b@x.com."); that request starts the model's cache afresh, a one-off cost. A passing rate limit or an overloaded provider doesn't change accounts: the request is retried as before. Nothing else changes accounts, and once the first has capacity again, requests go back to it. When every account is spent, the run fails saying when the first resets, or that they're out of credit. Each subscription's usage is read and shown on its own.

Only {{user}} can sign in, because it takes their account. An agent can't do it for them; it can tell them where to click. Models appear once their provider is signed in. An agent set to a model whose provider isn't signed in shows "No model available" and can't run until someone signs in or picks another model.

### The settings file

Everything in the sidebar and Settings, except signing in, lives in the settings file `{{config}}`. Edit it with your file tools and Claktory applies the change within a second, in every open window. So an agent can do for {{user}} nearly anything they could do by clicking.

```json
{
  "compact_at_tokens": 400000,
  "default_model": "anthropic/claude-opus-5-5",
  "default_effort": "high",
  "projects": [
    { "id": "web-site", "name": "Web Site", "path": "{{workspace}}/web-site",
      "folders": [ { "id": "research", "name": "Research", "path": "{{workspace}}/web-site/research" } ] }
  ],
  "agents": [
    { "id": "rivet", "color": "blue", "name": "Rivet", "role": "Admin", "prompt": "…", "model": "anthropic/claude-opus-5-5", "effort": "medium",
      "placeholder": "Set up a team that works on my codebase while I sleep\nSet up agents that build and run the website for my bakery",
      "avatar": { "shape": "hexagon" }, "extensions": { "agents": { "reachable": false, "admin": true } } },
    { "id": "nina", "color": "violet", "project": "web-site", "name": "Nina", "role": "Writer", "prompt": "Write the site's copy.", "model": "anthropic/claude-opus-5-5", "effort": "medium",
      "extensions": { "agents": { "also": ["designer"] }, "checklist": { "enabled": true } } }
  ]
}
```

- `compact_at_tokens`: the compaction threshold, above 0.
- `highlights`: `false` when {{user}} has turned highlights off (Settings → Display); left out, they're on.
- `task_alert_hours`: how long a background task runs before admin agents are told of it, once (24 unless changed).
- `resources`: when agents with the Resources extension are told the machine runs low (Settings → Resources): `ram_percent` (memory used, 1 to 100; 90 unless changed), `disk_free_gb` and `disk_free_percent` (a volume Claktory uses has less free than either, whichever is smaller; 10 and 10; `disk_free_gb` 0 turns it off) and `cpu_percent` (processors busier than it, 0 to 100; 0, off, unless changed); and `build_cache_gb`, the budget for one checkout's or project folder's build caches, in GB (25 unless changed; 0 never clears them; see Own checkout). Every key is optional.
- `display`: how wide {{user}} dragged the app's sidebar (`sidebar_width`) and the panel on the right (`panel_width`), in logical pixels, the same on every device; 0 or left out is the app's default, and the app keeps them within its range. Both are optional; a negative width makes the file invalid.
- `compaction`: `idle`, whether idle agents compact before their prompt cache expires (on unless `false`), and `idle_short_cache`, also when the cache lasts 5 minutes (off unless `true`). Optional.
- `prompt_cache`: how long prompt caches are asked to last, `"5m"` or `"1h"`, by provider (`"anthropic"`, the only one whose lifetime Claktory chooses) or model (`"anthropic/claude-opus-4-8"`, which wins over its provider). Left out: the provider's default, 5 minutes. Optional.
- `user`: the person agents work for: `name`, their first name, which agents and Claktory's texts call them by (Settings). Optional; left out, they say "the person".
- `remote`: the private tunnel for devices on other machines (see "Claktory on another machine"): `relays`, the relays' URLs, left out for n0's. Whether devices may connect follows the devices paired, not this. `port` and `listen`, from the listener before the tunnel, are still read but unused.
- `default_model`, `default_effort`: what new agents get when none is chosen.
- `projects[]`: `id`, `name`, `path`, the absolute path of its folder, and `folders` (optional): each with an `id` (unique within the project), a `name` and a `path`, absolute and anywhere.
- `agents[]`: `id`, `name`, `role` (what it does, shown with its name to {{user}} and to other agents, such as "Coordinator"; left out, it has none), `prompt`, `model` (`"<provider>/<model id>"`), `effort`, `color` (one of the eight; it belongs to the agent, so moving the agent in the list never changes it; left out, Claktory picks one, as for a new agent, or keeps the one the agent had, and writes it into the file), `project` (a project's id; leave it out for the workspace), `parent` (the id of the agent it sits under in the sidebar, in the same project; leave it out for the top level), `folder` (the id of one of its project's `folders` to work in; left out, or one the project doesn't have, it works in the project's own folder), `placeholder` (what its message box says when empty, such as what the agent is for; left out, it says "Message <name>"; several lines separated by `\n` are examples that take turns, such as Rivet's), `avatar` (its character's shape, drawn in its color: `{"shape": "hexagon"}`, with shapes circle, square, triangle, diamond, pentagon and hexagon; left out, or a shape Claktory doesn't know, it's automatic, picked from the agent's id so it never changes when the agent is renamed or moved; display only), and `extensions`.
- The order of `agents` is the order of the sidebar: within each project (and the workspace), and among each parent's agents, agents show in the order they come in the list. A `parent` that doesn't exist, is in another project or would make a loop is ignored (the agent shows at the top level) without making the file invalid.
- `extensions`: the agent's extension settings by extension id. Every key is optional; anything left out takes the extension's default. `enabled` turns an extension on or off for the agent. Messaging's options (under `agents`): `reachable`, `admin` and `see_map` (true or false) and `also` (a list of agent ids). Checklist's option: `nudge` (true or false). Tasks' option: `see_all` (true or false). Memory, Monitors, Resources, Highlights, Own checkout (`tree`), Viewer and Web have only `enabled`, and so do instances, by their key: `"memory:factory": {"enabled": true}` gives an agent the Claktory manual, `{"enabled": false}` takes it from an admin agent. Settings for an extension Claktory doesn't have are kept and ignored; a value of the wrong kind (`"admin": "yes"`) makes the file invalid.
- Ids use only a-z, 0-9 and -, and are unique among projects and among agents. Names can't be empty. Efforts are off, minimal, low, medium, high, xhigh or max; use one the model lists. Use models from the list of available ones below; others won't run.
- If an edit leaves the file invalid, Claktory keeps the last good settings and the sidebar shows the error until the file is fixed. Check your edit and fix it right away.

How to:
- **Add a project:** add it to `projects` with `path` set to `{{workspace}}/<id>`, and create that folder (`mkdir -p`).
- **Add an agent:** add it to `agents`. A new agent starts with an empty conversation.
- **Move an agent:** set its `project`, or remove `project` to move it to the workspace. It works in the new folder from its next step. Its `folder` belongs to the old project, so remove it or set one of the new project's. Move the agents under it too (set their `project` as well), or they're shown at the top level of the old project.
- **Set up folders in a project:** add them to the project's `folders`, e.g. `{ "id": "app", "name": "App", "path": "/Users/me/code/app" }`, create any folder that doesn't exist yet (`mkdir -p`), and set `folder` on each agent that works there. It works there from its next step. To remove a folder, take it out of `folders` and take `folder` off its agents; its files stay.
- **Reorder or nest agents in the sidebar:** move entries within `agents` to change their order, and set `parent` to put an agent under another one in its project (remove `parent` to bring it back to the top level). Nesting only changes how the sidebar shows them; it doesn't change who can message whom.
- **Change an agent:** edit its `name`, `color`, `prompt`, `model`, `effort`, `placeholder` or `avatar`. This includes you: your own entry is how you change yourself. The change applies from the agent's next step, even mid-task, and it's told in a short note what changed. `color`, `placeholder` and `avatar` apply at once: they only change what the app shows.
- **Delete an agent or project:** remove its entry. Deleting in the app also erases the conversation; removing the entry leaves the conversation's files in `{{home}}/agents/<id>`, and an agent added later with the same id picks it back up.
- **Change defaults:** edit `default_model`, `default_effort` or `compact_at_tokens`.
- **Turn an extension on or off for an agent:** set `extensions.<id>.enabled`, e.g. `"extensions": {"checklist": {"enabled": true}}`. The agent is told before its next step; an extension turned on can be used from then on (through `extension_call` until the agent's next context), and one turned off has its tools refused at once.
- **Let an agent message agents in other projects:** add their ids to its `extensions.agents.also`; for a conversation both ways, add each to the other's. `admin: true` lets it see and message everyone; `reachable: false` stops all agents from messaging it.

Agents can't yet sign in to providers or stop other agents; those need the app. When something can only be done in the app, tell {{user}} exactly where to click.

## Where Claktory keeps things

- `{{config}}`: the settings.
- `{{workspace}}`: the workspace folder, with one folder per project.
- `<project folder>/.factoryignore`: what the explorer hides in that project.
- `{{home}}/releases/`: published versions of Claktory, which the app offers as updates (built here, or downloaded by a Claktory installed online). Once a device on another machine has updated from one, it also holds that version's app packed for devices (`app.tar.gz`).
- `{{home}}/factory.db`: Claktory's records, in SQLite. `messages` holds every message an agent was sent, {{user}}'s and events (`source` is person, factory, agent, task or monitor; `sender`, - `{{home}}/remote/`: what devices on other machines need: Claktory's tunnel key (`iroh.key`; its public half is the `e=` in pairing codes), this machine's app's code (`local-pairing`), the port devices on other machines reach it on (`remote-port`, kept so it stays the same), and the paired devices (`devices.json`: each one's `id`, `name`, the SHA-256 of its token, the key it bound, when its unused code expires, when it was paired and last connected). Use `factoryd pair`, `unpair` and `devices` rather than editing it.
- `{{home}}/vault/`: the secrets (Settings → Secrets), kept apart from factory.db: `vault.db`, with every value encrypted, who has each secret and the log of their use, and `auto.key`, the key that opens it when Claktory starts (gone while signed in to claktory.com: the account opens it then). Only {{user}}'s account can read them. Never copy, edit or delete them.
- `{{home}}/account/`: the sign-in at claktory.com, if any: `account.json` (the service and its key, the email, this Claktory's id and token, and what was last sent, with the hours not yet sent), `claktory.key` (this Claktory's key there) and `share.key` (this machine's half of the vault's key while signed in). Never copy, edit or delete them.
- `{{home}}/trees/<agent id>/`: the agent's own checkouts (Own checkout extension), one per repository, each with a `.json` beside it saying which repository it's of. Claktory makes and removes them.
- `{{home}}/agents/<id>/`: each agent's conversation, its database (`database.sqlite`, Database extension), in `tasks/` its background tasks' logs, in `monitors/` its monitors' watch logs and file baselines, and in `archive/<time>/` conversations cleared with /clear (time in milliseconds since 1970). Claktory writes these; don't edit them.
